## Initialization and crash safety

The exact 26.2.2 namespace collision is confirmed: default teams include `admin` and `user`; users share their subject namespace; requested user IDs are lowercased. Security completion occurs before runtime persistence. Failed security creation can leave H2 present without completed runtime. The supplied production trace matches this mechanism, but production file/subject state remains unknown. Repeated setup on an existing user can change its supplied password and memberships, so missing runtime never authorizes an automatic retry.

Disk state distinguishes pristine, configured candidate and recovery-required. It deliberately cannot prove account integrity without starting the application. Existing configured candidates start without `CB_ADMIN_*`, `CB_SERVER_NAME` or `CB_SERVER_URL`; readiness proves supported authenticated account and registry access afterward. A durable attempt marker is created before the first application launch and does not override valid runtime/H2. Unknown or interrupted state stops before H2 is opened. No SQL, H2 replacement, account deletion, credential-file deletion or runtime synthesis is implemented.

The lock coordinates only guarded writers on filesystems with working `flock`; it cannot exclude legacy/manual launchers or guarantee multi-node filesystem behavior. The rollout therefore stops all writers before backup or repair. Interrupted atomic JSON writes leave original or complete replacement data, with private backup; unknown leftover temporary state fails closed on a new installation. Synchronous H2 commits reduce abrupt-process-loss exposure, but do not certify storage against power failure or filesystem corruption.

A controlled exact-image experiment compared independent default and synchronous databases: acknowledged `createUser` results followed by kill after 64/64/72 ms lost the newly created account in all three default cases; kill after 69/68/68 ms retained it in all three `WRITE_DELAY=0` cases. This isolates the H2 flush difference rather than attributing every restart symptom to initialization. H2 documents a default 500 ms write delay and supports the URL setting. The setting persists in the database. Reopening a previously default-configured workspace with the URL change preserved the `.database-credentials.dat` hash and original administrator login; no management username/password override is supplied. This establishes preservation, not the provenance of every effective credential in a production installation. See [H2 SET WRITE_DELAY](https://h2database.github.io/html/commands.html#set_write_delay) and the inspected [CloudBeaver database configuration](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.service.security/src/io/cloudbeaver/service/security/db/CBDatabase.java).

Readiness validates application setup, expected authenticated identity, enabled H2-backed administrator lookup and registry access. It does not certify every user's data, encrypted store or remote database. Its supported authentication can create normal session/audit writes; it never calls user creation, setup or credential-update APIs. Verification inputs are removed from the launched application process; exec probes obtain the original container environment. Probe cookie and failure state are private ephemeral files. A failed authentication remains unavailable until approved diagnosis/restart; TCP liveness does not repeatedly restart a running server for a bad verification password.

The actual image launcher starts as root, adjusts ownership, and runs Java as 8978:8978. Tests confirm generated JSON ownership/mode 8978:8978:600, a writable full-workspace mount and lifetime lock across the UID switch. An imposed nonroot Pod security context would break that launcher; this change retains the image's supported context. Hardening it further requires separate image/lifecycle validation.

## Remaining risks and rollout boundary

- Private plaintext connection seeds and backup archives remain secret-bearing. Production encrypted stores, original credential access, all user projects and real data integrity have not been established by synthetic tests.
- Verification requires a working local administrator credential source. Existing external-auth-only or stale-Secret installations need an evidence-backed alternative design/reference and clone proof; never create/reset an account to bypass the gate. Supported session/authentication activity and default root launcher privileges remain within the image's trust boundary.
- The same file URL with `WRITE_DELAY=0` adds synchronous I/O and may affect slow production storage. Local rapid-kill tests passed, but power loss, disk-full behavior, node loss and production latency remain unverified. Runtime persistence is owned by upstream; uncertain crash state blocks recovery rather than overwriting it.
- Image tags remain versioned rather than digest-qualified in existing manifests. Compare actual deployed/candidate digest before rollout; differing bytes require validation. k3s-specific behavior, actual Traefik/Cloudflare routing, External Secrets and Argo end-to-end prune/self-heal are not certified by kind.
- Argo PVC annotations protect only their documented controller operations after application. They do not protect manual/namespace deletion, unguarded writers or node-local storage loss. See [Argo sync options](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/).

The exact proposed sequence, A/B/C/D preconditions, backup requirements, validation, rollback and stop conditions are in [CloudBeaver recovery](../workflows/cloudbeaver-recovery.md). Required approvals cover the Git-managed hold/merge boundary, clean writer stop, backup Jobs and restore rehearsal, any B/C repair, final sync/restart acceptance and re-enabling automation. A workspace/H2 restore or production database connection needs separate authorization. Branch pushes and Draft PR updates are authorized for peer review. Merging to `main`, production restart/scaling, Secret/PVC changes, Argo operations and issue closure remain unauthorized.
