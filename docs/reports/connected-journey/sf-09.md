# SF-09 Customer support and feedback: connected journey plan

## Position

SF-09 opens and closes the customer's story. Part 1 (story step 3, before SF-07/WF-01) walks **SF-09-A2**: a visitor
self-registers `Journey Foods {TAG}` on the portal, sets the portal language, adds a contact and uploads a logo; the
account is the customer every later flow orders and delivers for. Part 2 (story step 17, after WF-06, SF-03 and SF-04)
walks the **main path** (support request about the journey order, answered by the order's salesperson, read by the
customer, then closed by Sales) and **SF-09-A4** (the customer rates the completed order once; Sales and the Head of
Sales see the feedback). SF-09-A1, SF-09-A3 and SF-09-E1 are not walked; A3 is the documented fallback (finding 2),
E1 is not clickable (finding 6).

## Connection findings

1. **Self-registration works by clicks with no e-mail step.** Odoo's `auth_signup` data sets `auth_signup.invitation_scope = b2c` (`auth_signup/data/ir_config_parameter_data.xml:5`, noupdate) and nothing in `sol_*` or `sol_demo` overrides it; no captcha module is installed. `web_auth_signup` signs the user in right after `do_signup` (`auth_signup/controllers/main.py:46-73`); `CustomerSignup._prepare_signup_values` (`sol_commerce/controllers/signup.py`) and `ResUsers._signup_create_user` (`sol_laboratory/models/master_data/res_users.py:21-31`) create the `medilab.customer` (company partner + the person as `default_contact_id`). No confirmation link exists for a new account. The "account created" e-mail is sent with `force_send=True`; the local `src/core/config/odoo.conf` has no SMTP server, so it fails into the audit log (`mail_mail.py:62-74`) without blocking. Verify on the live app that nobody switched the setting to `b2b` in General Settings (then `/web/signup` is 404 and the link is missing).
2. **What makes the new user a customer who may order:** only the `medilab.customer` record from step 4. No sales terms are created, so `allow_credit` is false: WF-01 must send the quotation with an advance (Head of Sales could set `medilab.customer.sales.terms`, `sol_commerce.menu_customer_sales_terms`, but the story does not need it). If self-registration were closed, the fallback SF-09-A3 is: Sales creates the customer, clicks `button[name=action_invite_to_portal]` and `button[name=action_grant_access]` in the portal wizard; the invitation link is only in the e-mail. Without a mailbox the nearest click path is the administrator in debug mode, Settings → Technical → Emails (the invitation mail, kept unsent without SMTP) to copy the `/web/signup?token=…` link, or Settings → Users → the portal user → Action → Change Password. Both are administrator workarounds, not customer screens.
3. **Rating depends on WF-06 issuing the report, not on payment.** `can_give_feedback` needs `order_status == completed` (`sol_commerce/models/support/sale_order.py:44-46`), set only in `TestRequest._set_status("reported")` while the order is `confirmed` (`sol_commerce/models/orders/test_request.py:52-58`), which `_issue` calls (`sol_laboratory/models/testing/test_report_issue.py:133-151`). If WF-06 cannot issue by clicks (Viettel Sign enabled: `_digital_sign` waits for the external signature, `test_report_issue.py:161-166`), SF-09-A4 is blocked: the order page shows no feedback form. A WF-05 subcontracted test that never completes also blocks it, since the report cannot be issued before every sample completes.
4. **The support request reaches the order's salesperson only if WF-01 claimed it.** `create` copies `order.user_id` into `handled_by_id` (`support_request.py:107-118`); the to-do task is created only when that user has a `medilab.person` (`_create_task`, `support_request.py:131-137`), true for `demo.sales`. If WF-01 used another salesperson, step 16 must sign in as that login; with no `user_id` the request falls into SF-09-A1 (untaken, `Take` button).
5. **Customer notification of the answer is e-mail only.** The reply notifies the customer partner (follower) by e-mail; there is no SMTP locally and no mailbox in the journey. The click check is the portal page (step 19). Whether a support answer also appears under `/my/notifications` was not found in the code: treat as not shown.
6. **SF-09-E1 is not clickable.** A permanent bounce is set only by Brevo's webhook (`mail_notification.py` `_notification_for_brevo`) or by the `notifications.email` scheduled job after the SMTP retries run out (`scheduled_job.py:134-142`, `_schedule_email_retry`/`_mark_email_bounced`, `mail_notification.py:238-275`): both external or cron. The corrected address's confirmation link (`res_partner.py:46-86`, route `/medilab/email/confirm/<token>`) only exists in a `mail.mail` body (the token is stored hashed), readable only by the administrator in debug mode under Settings → Technical → Emails. The demo bounced customer `demo.registered` lets the "notice stays in the portal" part be seen, but that is outside the journey's customer.
7. **Closing a request is a Sales action only.** The portal has no close button (`support_templates.xml`); the diagram's "customer reads → closed" is done by Sales `action_close` (step 23). business-flows.md does not say who closes.
8. **Back-office labels are Vietnamese for every Sales actor** (`demo.sales`, `demo.head_of_sales` are `vi_VN`): the spec must use menu xmlids, `name=` handles and paths, not English labels.
9. **Cypress RPC shortcuts this plan replaces:** `orderIn("completed")` creates an order directly in `completed` (`flows/sf-09-support-feedback/setup.js:26-60`), `openRequest`/`rateOrder` post forms over HTTP, and the specs open records by URL (`cy.openRecord`). The journey gets the completed order only through WF-01 → WF-06 and opens every record from menus and portal links.
