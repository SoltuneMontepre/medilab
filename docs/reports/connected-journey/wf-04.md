# WF-04 Result entry and approval: connected journey plan

## Position

Story step 11. It follows SF-05, which leaves the journey booking scheduled again on a machine back in use, and
precedes WF-05, which outsources the sample's second test. The journey walks the main path without result files
(`Start booking` → `files? no` → `Enter result with snapshot unit and LOD/LOQ` → `comparison requested? no` →
`Check measurement and any sanity warning` → `Send and sign` → `Notify the head` → `approve` → `Every remaining test
approved? no` → `Wait for other tests`), with WF-04-A4 (no requested comparison, no conclusion). WF-04-E2 shows only as
the check that no warning appears (see finding 6). Files (F-53 to F-57, WF-04-A6 to A10, E4 to E6) are out of the
click journey; see finding 2.

## Connection findings

1. **Starting the booking is optional in the code.** Saving a result picks the latest scheduled or in-progress
   booking of the test and sets it `done` (`sol_laboratory/models/testing/test_result.py:348-378`, `_compute_measurement`
   at 310-326); the test goes to testing on result creation (`tests._start()`). So "Trigger: a booked test starts" is
   not enforced. The journey clicks `Start` anyway to walk the documented path.
2. **Result files are out of the click journey.** The back office cannot create a file or a version: file and version
   lists/forms are `create="0"` (`views/laboratory_files/laboratory_file_views.xml:9,24`,
   `laboratory_file_version_views.xml:8,27`); content arrives only through the Medilab Sync API or the ONLYOFFICE
   editor. With the empty SF-11 folders, the back office alone shows WF-04-A10 only (Laboratory → Documents → Folders /
   Files / File Versions, `sol_laboratory.menu_laboratory_folder`, `menu_laboratory_file`,
   `menu_laboratory_file_version`) and nothing to sign or reject (E5, the head's version signing) until a file was
   uploaded by Sync. WF-04-A6 to A9, E4, E6 need Medilab Sync or ONLYOFFICE.
3. **A future booking can be started now, and its time is not corrected.** `action_start` checks only status
   `scheduled` and who runs it (`models/testing/machine_booking.py:328-331, 434-439`), not the clock. It does not move
   `starts_at`, so the result's `started_at` defaults to the booking's future start
   (`test_result.py:329-331`) and the calendar event stays in the future. The plan should accept that, or the tester
   corrects `.o_field_widget[name=started_at]` in step 7 (doubtful whether the owner wants a future start on record).
4. **"Mark machine busy/available" has no machine state.** Machine status is only `in_use`/`under_repair`/`retired`
   (`models/master_data/machine.py:52`); "busy" is the booking `in_progress`, "available" is the booking `done` set at
   result save, not at "submitting" as business-flows.md says. Nothing to check on the machine form.
5. **Regulation comparison (WF-04-A4).** The result asks for a conclusion only when the sample's regulation has a
   limit for the parameter on some sample type (`sample_test.py:361-364`); the conclusion radio is hidden otherwise
   (`views/testing/test_result_views.xml` block `o_test_result_conclusion`). The journey parameter is new, so no
   regulation limits it: no conclusion, no pass/fail. For a comparison the journey would need, before the result is
   saved (the limit is copied at creation): SF-08 adds a limit line for `Journey nitrate {TAG}` on the demo sample type
   (exact type, unit, max) to a regulation, and WF-01 picks that regulation for the sample on the order (the sample's
   `regulation_id` is an agreed field, `sample.py:87`). Then step 7 adds choosing `Pass`/`Fail`/`Insufficient Basis`
   in `.o_field_widget[name=conclusion]`, and a value near the limit would also walk WF-04-E2.
6. **WF-04-E2 cannot be shown with a new parameter.** The spread warning needs at least the configured minimum of
   approved results of the same way and sample type (`models/testing/test_result_check.py:71-90`); the new way has
   none, and without a limit there is no limit warning. The journey can only assert that no warning shows.
7. **The test must be in Chemistry for the head to approve.** Both approval levels are `same_department`; the
   department is that of the testing task (`test_result.py:538-540`). SF-08's way and WF-03's task must be in
   `demo_hr_department_chemistry`, the department of `demo.tester` and `demo.head_of_department`.
8. **Task Start is a different button.** The testing task form has its own `Start` (`button[name=action_start]` on
   `medilab.task`, `views/tasks/task_views.xml:66-72`) that only sets the task in progress; it does not start the
   booking. The plan uses the booking's `Start` on the sample test's Bookings tab.
9. **Head notification is an Odoo inbox message plus the dashboard tile.** There is no approval task; the head reaches
   the result through the systray inbox or the Tasks dashboard "To approve" tile (`models/tasks/task_approvals.py`).
   E-mail and push delivery are queued jobs, not part of the click journey.
10. **Cypress shortcuts this plan replaces:** `setup.js` builds the sample, assignment, booking and start over RPC
    (`receivedSample`, `assign`, `book`, `callAs(... "action_start")` at `setup.js:66-90`) and sends/approves results
    with `callAs(... "action_sign")` (`setup.js:33-63`). The main Cypress case `TC-WF04-M` enters a result on an
    assigned test without any booking being started.
