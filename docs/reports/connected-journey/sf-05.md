# SF-05 Machine calibration and unavailability: connected journey plan

## Position

Story step 10, between SF-10 (step 9) and WF-04 (step 11). The journey's test `Journey nitrate {TAG}` holds a scheduled booking made in WF-03. The administrator puts the booking's machine under repair. The same booking returns to the plan as proposed and moves to the other machine linked to the same testing method. The head of department approves it there, so it is scheduled again. The administrator then records the repair and a calibration after it, and puts the first machine back in use. That machine has already given up the booking, which stays scheduled on the other machine for WF-04. The journey walks the SF-05 main path, including its rule that a repaired machine returns to use only after a calibration dated after the repair. The return to use is first refused, then accepted. SF-05-E1 (no other machine, so the work stays unplaced) is the fallback variant B and is used only if SF-08 links a single machine. SF-05-A1, A2, A3 and E2 are not walked.

## Connection findings

1. **No notice when the machine's downtime moves the booking.** The main path says not-started bookings move "with notices to the tester and head". `Machine.write` → `_requeue` (`models/master_data/machine.py:102-106`, `models/testing/machine_booking.py:545-558`) sets the booking back to proposed and replans it, and raises no event. Only leave and an unavailable room notify, through `_return_to_plan` (`machine_booking_interruptions.py:131`). The Cypress README lists this as not built (`src/tests/cypress/e2e/README.md:126`). Consequence: the head does not find the moved booking in a notification or to-do. The journey reaches it through Machine Schedule → list → search (step 5). The tester is notified only when the head approves (`machine_booking_approval.py:100-119`, event `machine_booking.approved`).
2. **Server error when a booking on a machine under repair is opened.** `_compute_machine_warning` evaluates `machine._usable_until() - windows["calibration_warning_days"]` (`models/testing/machine_booking_conditions.py:44-46`). `_usable_until()` returns `datetime.min` for a machine not in use (`machine.py:121-122`), so the subtraction overflows for any booking with a slot on a calibrated machine under repair. `setup.js:608` works around this by never reading `machine_warning`. The field is on the booking form (`machine_booking_conditions_views.xml:9-14`) and is an optional column of the Machine Schedule list (`:27`). The journey's own booking leaves A before anyone reads it. Done bookings on `UVVIS-01` from earlier journey runs keep their slot, though, and opening one between steps 3 and 10 would hit the error: a list without the "Not Finished" filter, or the calendar popup. Steps 1-11 stay in the list with "Not Finished" and the run's `{TAG}`. Report it as a defect.
3. **Return to use replans every proposed booking, and its order decides the hand-over.** Setting A back to In use runs `_requeue` → `_plan` for every department with proposals (`machine_booking.py:557-558`). A proposed booking that A and B could both take goes back to A (code order). The journey therefore has the head approve on B while A is under repair (steps 5-6, the States line "scheduled on another machine"). If the stitched journey moves the approval after step 10, WF-04 receives the booking on `UVVIS-01`, with the "was repaired on" warning. Each step also recalculates the plans of other departments and may send demo at-risk notices (`machine_booking_plan.py:69-71`).
4. **SF-08 must give a second machine for the same method; the demo has none for a quiet method.** The SF-05 main path needs another machine linked to the booking's method (`_recommend` only searches `machine.method` links of the way's method, `machine_booking.py:597-603`). `UVVIS-01` is the only machine for `LAB-CR6-01`. SF-08 must create `UVVIS-JOURNEY` by clicks: Machines → New, then the Service History and Testing Methods tabs. Without it, the journey walks variant B (SF-05-E1). Creating a new B with a tagged code on every run would leave earlier runs' machines linked to `LAB-CR6-01`. The booking would then move to the oldest of them (lowest code), so step 4 could only check "not A". Hence the fixed code, reused across runs.
5. **WF-03 might book B instead of A.** This happens if the tester or room is busier around A's slot, or if B's duration is shorter. The steps take machine A from the booking (step 1) and need the two machines only as "the booking's machine" and "the other one". If the booking is on `UVVIS-JOURNEY`, put that machine under repair and expect `UVVIS-01`. Machine B then never had a repair, and the step 8 refusal applies to it in the same way.
6. **The test's due date has to leave room on B.** After step 3 the plan looks for B's earliest slot by the test's due date and the tester's working time (`machine_booking.py:571-575, 610-629`). If SF-07 accepted a requested date that is very close, B may have no slot. The booking then stays unplaced and outsourcing is suggested (variant B behaviour), even with B linked.
7. **Mismatch with business-flows.md.** It says "returning to use requires all calibration, maintenance and availability conditions to be satisfied". The code checks only the repair rule on the status change (`machine.py:87-100`). An expired calibration or overdue maintenance does not stop In use; it only blocks booking (`machine_booking_conditions.py:100-120`). This does not affect the journey, because step 9 records a valid calibration.
8. **The same booking record moves.** No new booking is made, and the booking's own `starts_at` is cleared and set again (`machine_booking.py:556`, `machine_booking_plan.py:100-108`). Proposed bookings are left out of the audit trail (`machine_booking_plan.py:26-28`), so the move from A to B shows nowhere except the booking's current machine. Flows that read the history (WF-04, SF-03) see only the approval on B.
