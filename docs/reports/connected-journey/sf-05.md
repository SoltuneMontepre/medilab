# SF-05 Machine calibration and unavailability: connected journey plan

## Position

Story step 10, between SF-10 and WF-04. The test `Journey nitrate {TAG}` holds a scheduled booking, pinned by the head in SF-10. The spec `src/tests/playwright/journey/09-sf-05-machine-unavailability.spec.js` walks the SF-05 main path: the administrator puts the booking's machine under repair, the booking returns to the plan and is proposed on the other machine linked to LAB-CR6-01, and the head approves it there while the first machine is still under repair. ## Data

- On the run the booking left 11:00 to 12:00 on UV-Vis spectrophotometer 1 for 09:15 to 10:15 of the same day on UV-Vis spectrophotometer (journey): urgent since SF-10, it took the earliest free slot.

## Connection findings

1. **Nobody is told that the downtime returned the booking to the plan.** The main path promises notices to the tester and the head. No notice is created for either: they find the proposal by searching the Machine Schedule. The tester is told only when the head approves the new slot. The spec reports the tester's missing notice as a failed check.
2. **The downtime drops the slot the head pinned.** The booking loses its pin and its slot and takes the earliest slot on the other machine, here earlier than the slot the head chose in SF-10.
3. **The Machine Schedule fails for bookings that keep a slot on a calibrated machine under repair.** A finished or cancelled booking keeps its slot. Working out its machine warning for such a machine raises a server error, `OverflowError: date value out of range`, and the list shows "Oops! Something went wrong". Reproduced on the live application outside the story: ICP-MS 1 put under repair, then Machine Schedule → list view without the filter Not Finished. The calendar and the list filtered on Not Finished opened. The journey's own booking leaves the machine before anyone reads it and the repaired machine holds no other booking on a first run, so the spec's look at step 4 passes there; it fails once an earlier booking kept a slot on the machine.
4. **The administrator can approve the booking too.** Holding every permission, the administrator sees Approve on the proposed booking; the journey leaves the approval to the head.
5. **The status bar of a machine saves nothing by itself.** A click on Under repair or In use changes the form only; the bookings move when the form is saved.

Read in the code, not walked: returning a machine to use recalculates every proposal, and a proposal still open then goes back to the first machine, whose code comes first, which is why the head approves while it is under repair; the return to use checks only the repair rule, not an expired calibration or an overdue maintenance, which block bookings instead; a booking placed on the repaired machine within 7 days shows a "was repaired on" warning.
