# WF-06 Report signing, release and delivery: connected journey plan

## Position

Story step 14. It starts when WF-05 approves the last outsourced result: that approval completes the test request, which creates the draft report and the Lab Head's signing task in the same transaction. SF-01 has already paid the order in full. The journey walks the main path with WF-06-A4: digital signing stays disabled, as in the demo data. Two more paths come from orders and cannot be avoided. WF-06-A1 applies because an order's request is always delivered in person, so recording the delivery sends no e-mail. WF-06-A2 applies because an order's request always asks for a bilingual report. WF-06-E4, where the ONLYOFFICE conversion is down, is the one exception the journey can run into. See finding 1. SF-03 later sends a replacement report through this flow again.

## Connection findings

1. **No report PDF can be prepared on this stack: the ONLYOFFICE gateway refuses Odoo's conversion path, so the journey stops at step 4.**
   - Odoo posts the conversion to `{ONLYOFFICE_INTERNAL_URL}/converter` (`sol_laboratory/services/report_conversion.py`, `CONVERTER_PATH`). The local gateway (`tools/onlyoffice/proxy.py`, `_internal_route`) routes only `/healthcheck`, `POST /ConvertService.ashx` and `/cache/files/`, and answers 400 to anything else. `tools/onlyoffice/verify.py` checks only `/ConvertService.ashx`, so `task onlyoffice:verify` passes.
   - The health check passes, so the Lab Head does not see "ONLYOFFICE is unavailable"; **Prepare PDF** shows "ONLYOFFICE could not convert the document to PDF right now; prepare it again later." and changes nothing. The job item `report:<id>:0` keeps failing with the same message (WF-06-E4). The main app and the spare instance fail alike.
   - Fix (owner's decision): allow `POST /converter` in the gateway, or post to `/ConvertService.ashx`.
   - Consequence: the report stays a draft, so SF-03, SF-04, SF-09 part 2 (rating) and SF-02 (reorder of a completed order) lose their starting state. The spec marks "The report's PDF is prepared" red and stops without handing over report keys.
2. **The PDF is prepared by a cron, not a click.** The draft report and the signing task are created on the last result approval; `ir_cron_test_report_prepare` prepares the PDF. A failed attempt is counted and retried later. The spec waits 90 s, opening the report again, then clicks **Prepare PDF**, which prepares synchronously.
3. **Orders always produce a bilingual report delivered in person.** `_confirm_order` calls `create_from_order` without `report_language` or `delivery_method` (`sale_order_confirmation.py:313-322`), so the defaults `bilingual` / `in_person` apply (WF-06-A1, WF-06-A2). The e-mail delivery of the main path needs Sales to edit the test request's language and delivery method, which belongs to WF-01's owner.
4. **What "withheld for payment" blocks (SF-01 ↔ WF-06).** While the order is not paid in full, not on credit and not free, the report is issued but not offered in the portal, **Record Delivery** in Reports to Deliver is refused with "{REPORT} is sent once order {ORDER} is paid in full.", and the notice says it is released once paid. A late payment sends no new notice. The journey's order is paid in full by SF-01, so none of this applies.
5. **The candidate is frozen to the printed business data.** If the customer profile or a result changes between steps 5 and 6, the PDF stops being current, **Sign** disappears and a new PDF is prepared, which needs the conversion again.
6. **The Lab Head is not notified.** The draft creates the role task "Ký phiếu kết quả: Draft report of `{REQUEST}`" in the Department Queue (its name keeps the Vietnamese task type even on English screens) and no message. business-flows.md says the Lab Head is notified. The task closes on approval; signing happens on the report form.
7. **The order page has no report link.** `sol_commerce.order_page` shows the status and the feedback form, not the report. The only download is Test Reports on the portal home `/my/home`, which the user menu's **My Account** opens. Soft check, red.
8. **The customer sees the order Completed before the report is issued.** The portal badge shows `customer_status`, which maps the request status `completed` to Completed (`sol_commerce/models/orders/sale_order_customer.py`, `REQUEST_STATUS_TO_CUSTOMER`) while `order_status` stays confirmed until issue. business-flows.md: "order completed only on issue". The page also still offers **Request cancellation**. Soft check, red.
9. **Whether the customer is told the results are ready is uncertain.** The issue raises `result.released` ("The results of order ... are ready. Download report ... from your portal."), but the subtype is not a default notification and the demo customer received no portal notice for `PKQ.2026.0001`. Soft check.
10. **The accredited nitrate test gets no mark on the report.** SF-06 made the journey's nitrate test accredited (`is_accredited` is true), but the report prints only the quality registrations' marks (`quality_registration.py:41`, such as `(*)` after "Lead (Pb)" in the demo PDF). business-flows.md SF-06: "reports carry the accredited and registered marks". Soft check; the mark found is handed over as `nitrateMarkOnReport`.
11. **E-mail is not needed.** In-person delivery and the `result.released` notice are handled inside Odoo.
