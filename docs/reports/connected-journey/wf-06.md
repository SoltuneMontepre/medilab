# WF-06 Report signing, release and delivery: connected journey plan

## Position

Story step 14. It starts when WF-05 approves the last outsourced result: that approval completes the test request, which creates the draft report and the Lab Head's signing task in the same transaction. SF-01 has already paid the order in full. The journey walks the main path with WF-06-A4: digital signing stays disabled, as in the demo data. Two more paths come from orders and cannot be avoided. WF-06-A1 applies because an order's request is always delivered in person, so recording the delivery sends no e-mail. WF-06-A2 applies because an order's request always asks for a bilingual report. WF-06-E4, where the ONLYOFFICE conversion is down, is the one exception the journey can run into. See finding 1. SF-03 later sends a replacement report through this flow again.

## Connection findings

1. **Without ONLYOFFICE Document Server, no report can be issued, so the journey stops at step 4.**
   - **Who converts:** `medilab.test.report.candidate._convert` (`sol_laboratory/models/testing/test_report_candidate.py:123`) calls `services/report_conversion.py:convert_to_pdf`. That function POSTs to `{ONLYOFFICE_INTERNAL_URL}/converter` with a JWT signed by `ONLYOFFICE_JWT_SECRET`, and Document Server fetches the DOCX from a presigned Garage address (`laboratory_bucket.read_address`, which is signed on `BUCKET_LABORATORY_PUBLIC_ADDRESS`).
   - **Health check:** before converting, `_prepare_pdf` (`test_report_preparation.py:160-173`) calls `_check_editing_available` (`laboratory_editing_session_callback.py:52`). The check needs `ONLYOFFICE_JWT_SECRET` (at least 32 bytes) and `GET {ONLYOFFICE_INTERNAL_URL}/healthcheck` answering `true` (`services/editing_service_health.py`).
   - **Signing needs a prepared PDF:** **Sign** is shown only when `approval_can_sign` is true, and `_approval_check_actor` → `_check_signable_candidate` (`test_report_issue.py:44-66`) refuses without a current candidate. There is no screen or demo path that issues a fresh report without a candidate. The demo makes candidates by patching `_convert` (`demo_report_templates.py:prepare_report`), and Cypress never issues a new report (`flows/wf-06-report-release/setup.js:84-86, 129-131`).
   - **What the Lab Head sees while it is down (WF-06-E4):** the form keeps the alert "The report's PDF is being prepared...". **Sign** never appears, and **Prepare PDF** (`button[name=action_prepare_pdf]`) stays visible. Clicking it shows the error "ONLYOFFICE is unavailable, so no new PDF can be prepared: Online editing is unavailable right now. Syncing, history and restoring still work." and changes nothing. **Reject** still works. The job keeps waiting and retries every 5 min (`test_report_scheduled_job.py:18`) without counting a failed attempt.
   - **What the stack needs:**
     - Images: `docker.io/onlyoffice/documentserver:9.4.0.1@sha256:3ab6ebc7...`, plus the `onlyoffice-gateway` and `onlyoffice-adapter` proxies (`docker.io/library/python:3.12.13-slim`, running `tools/onlyoffice/proxy.py`). See `src/applications/medilab-sync/docker-compose.yml` and `tools/onlyoffice/compose.yml`.
     - Odoo environment (`tools/onlyoffice/compose.yml`): `ONLYOFFICE_INTERNAL_URL=https://onlyoffice-gateway:9443`, `ONLYOFFICE_PUBLIC_URL`, `ONLYOFFICE_CALLBACK_ORIGIN`, `ONLYOFFICE_JWT_SECRET`, and `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE` pointing at the ONLYOFFICE CA bundle.
     - Commands: `task onlyoffice:setup` (prepares the editor and verifies a real conversion), then `task onlyoffice:up`, `task onlyoffice:verify` and `task onlyoffice:status`.
     - Host: an amd64 engine with at least 4 CPUs and about 4 GiB for ONLYOFFICE (`tools/scripts/local_setup.py:24, 100-124`).
   - **Consequence:** with only Odoo, Postgres and Garage, WF-06 ends at "draft report with signing task". SF-03, SF-04, SF-09 part 2 (rating) and SF-02 (reorder of a completed order) then lose their starting state.
   - **Nearest workable path:** start ONLYOFFICE through the `onlyoffice:*` tasks. A demo report cannot stand in, because the journey's records are new. Without ONLYOFFICE, run steps 1-3 plus the E4 check (Prepare PDF shows the error), and mark the rest blocked.
2. **The PDF is prepared by a cron, not a click.** The draft report and the signing task are created synchronously on the last result approval. The PDF is prepared by `ir_cron_test_report_prepare`, which `_open_signing_task` wakes (`test_report.py:248`) and which also runs every minute. The config has `workers = 0`, so Odoo runs threaded with cron threads. Step 4 must therefore poll by reloading. The Lab Head's **Prepare PDF** button is a click-only fallback: it shows while no current PDF exists and prepares synchronously. If the cron is off (for example with `--max-cron-threads=0`), use the button.
3. **The demo must have an available template version for the request's language.** `_default_template_version` (`test_report_preparation.py:134`) picks the latest available version of the first template of the report's language. Otherwise preparation fails with "No report template is available in the report's language yet." The demo seeds bilingual v2, vi v1 and en v1 as available (made available without a preview), but only if the Garage bucket answered at install (`demo_report_templates.py:35-37`). On a database installed without Garage, the administrator must make a bilingual template version available, and that needs ONLYOFFICE for the preview. Check that Laboratory > Configuration > Report Templates (`menu_report_template`) lists "Phiếu kết quả nước uống song ngữ" with an available version.
4. **What "withheld for payment" blocks (SF-01 ↔ WF-06).** `withheld_for_payment` (`sol_commerce/models/orders/test_report.py:24-33`) is true while the order is not paid in full, the order is not on credit and its total is not zero.
   - **Issue:** not blocked. Signing still issues the report, the request becomes `reported` and the order `completed`.
   - **Notification:** still sent at issue, as the order event `result.released`, but the text says the report "is released in your portal once the order is paid in full" (`:35-53`).
   - **Delivery:** refused with "{REPORT} is sent once order {ORDER} is paid in full." (`:56-65`). The form hides **Record Delivery**, but the Reports to Deliver list still shows the row and its button (its domain has no payment filter, `test_report_views.xml:290-296`), so the click shows that error.
   - **Portal:** the report is left out of `/my/test-reports` and its download (`_portal_domain`, `:68-72`).
   - **After a late payment:** confirming payment later sends no new "results ready" notice, because no hook re-raises `_notify_issued` (grep `sol_commerce/models`). The customer must check the portal themselves.
   - **Consequence:** SF-01 must reach `payment_status=paid` before step 6, or steps 10 and 13-14 fail and the order still turns `completed`.
5. **Orders always produce a bilingual report delivered in person.** `_confirm_order` calls `create_from_order` without `report_language` or `delivery_method` (`sale_order_confirmation.py:313-322`), so the defaults `bilingual` / `in_person` apply. The journey therefore cannot walk the WF-06 main delivery by e-mail (the `test_report:<id>:delivered` mail with the PDF) without Sales editing the test request's `report_language` / `delivery_method` on the back-office form (`test_request_views.xml:89`). Whether those fields stay editable once the request is `paid` is not settled (see "To verify"). That edit belongs to WF-01's owner.
6. **The candidate is frozen to the printed business data.** The snapshot holds the customer name and address, the result rows and the approvers (`_binding_values`). If anyone edits the customer profile (SF-09) or a result between step 4 and step 6, the candidate stops being current. The warning "The prepared PDF no longer matches ..." appears, **Sign** disappears, and the cron prepares a new PDF, which needs ONLYOFFICE again. Profile edits must not run in parallel with steps 4-6.
7. **The signing task closes automatically.** It is closed on approval (`test_report_issue.py:_approval_set_state`). Step 2a is a check only: there is no "start task" step for the Lab Head, and signing happens on the report form.
8. **The portal order page has no report link.** `sol_commerce.order_page` (`views/portal/catalog_templates.xml:259`) shows the status and the feedback form but no download link. The only download is `/my/test-reports`, reached from the portal home card. `ecommerce_module/features/customer.md` §4 does not say where the download is, so this is a documentation gap, not a break.
9. **How a commerce customer reaches `/my` by clicks is not certain.** The commerce header navigation (`navigation_templates.xml:24-31`) links only Catalog, My orders, Support and Account (`/my/account`). The "Test Reports" card is on the portal home `/my`, which Cypress opens with `cy.visit("/my")`. Odoo's user dropdown normally has a "My Account" link to `/my/home`. Whether it leads to the cards page in this theme is still open (see "To verify"). If no link reaches it, the only click path to the report is the "Results released" notification, if the portal shows it. Otherwise the journey has to type `/my` into the address bar, which breaks the click-only rule.
10. **E-mail is not needed.** In-person delivery and the `result.released` notice are both handled inside Odoo. The notice is stored as a `mail.message` whether or not outgoing mail works.
11. **business-flows.md says "the Lab Head is notified".** The code creates the role task and does not call `raise_event` for the Lab Head. Whether the task also posts a bell notification is not visible in WF-06's code.
