# WF-06 Report signing, release and delivery: connected journey plan

## Position

Story step 14. It starts when WF-05 approves the last outsourced result: that approval completes the test request, which creates the draft report and the Lab Head's signing task in the same transaction. SF-01 has already paid the order in full. The journey walks the main path with WF-06-A4: digital signing stays disabled, as in the demo data. Two more paths come from orders and cannot be avoided. WF-06-A1 applies because an order's request is always delivered in person, so recording the delivery sends no e-mail. WF-06-A2 applies because an order's request always asks for a bilingual report. WF-06-E4, a conversion outage, is not walked: if the PDF cannot be prepared, the spec fails at step 6 with the reason the Lab Head is shown. SF-03 later sends a replacement report through this flow again.

## Connection findings

1. **The local ONLYOFFICE gateway refused Odoo's `POST /converter` until it was fixed in this work.**
2. **The PDF is prepared by a cron, not a click.** The draft report and the signing task are created on the last result approval; `ir_cron_test_report_prepare` ("Prepare test report PDFs", every minute) prepares the PDF, about 50 s after the Lab Head first opened the draft on the spare instance. A failed attempt is counted and retried later. The spec waits 90 s, opening the report again, then clicks **Prepare PDF**, which prepares synchronously.
3. **Orders always produce a bilingual report delivered in person.** `_confirm_order` calls `create_from_order` without `report_language` or `delivery_method` (`sale_order_confirmation.py:313-322`), so the defaults `bilingual` / `in_person` apply (WF-06-A1, WF-06-A2). The e-mail delivery of the main path needs Sales to edit the test request's language and delivery method, which belongs to WF-01's owner.
4. **What "withheld for payment" blocks (SF-01 ↔ WF-06).** While the order is not paid in full, not on credit and not free, the report is issued but not offered in the portal, **Record Delivery** in Reports to Deliver is refused with "{REPORT} is sent once order {ORDER} is paid in full.", and the notice says it is released once paid. A late payment sends no new notice. The journey's order is paid in full by SF-01, so none of this applies.
5. **The candidate is frozen to the printed business data.** If the customer profile or a result changes between steps 7 and 8, the PDF stops being current, **Sign** disappears and a new PDF is prepared.
6. **The Lab Head is not notified.** The draft creates the role task "Ký phiếu kết quả: Draft report of `{REQUEST}`" in the Department Queue (its name keeps the Vietnamese task type even on English screens) and no message. business-flows.md says the Lab Head is notified. The task closes on approval; signing happens on the report form.
7. **The customer sees the order Completed from the last result approval.** The portal badge maps the request status `completed` to Completed (`sale_order_customer.py`, `REQUEST_STATUS_TO_CUSTOMER`), as customer.md defines it ("All samples completed"), while Sales' `order_status` stays confirmed until issue, as business-flows.md requires ("order completed only on issue"). Both are checked. The completed-looking page still offers **Request cancellation**, since that follows `order_status`.
8. **The customer is told the results are ready by e-mail unless they choose the portal.** Issue raises `result.released` on the order to its contact. The event is not a default portal notice, so it reaches the portal list only once the customer ticks **In the portal** for "Results released"; its title is the report number, not the event name. On this stack the e-mail cannot be checked: SMTP fails, and the retries of the mandatory payment receipt mark the contact's address bounced, after which no e-mail is queued. The spec ticks the box in step 2 and reads the notice in step 13.
9. **The accredited nitrate test gets no mark on the report.** SF-06 made the journey's nitrate test accredited (`is_accredited` is true), but the report prints only the quality registrations' marks (`quality_registration.py:41`, such as `(*)` after a registered parameter). The PDF prints "`Journey nitrate {TAG}` 12,50 mg/L LAB-CR6-01" with nothing after the name. business-flows.md SF-06: "reports carry the accredited and registered marks". Soft check, red; the mark found is handed over as `nitrateMarkOnReport`.
10. **The order page has no report link.** `sol_commerce.order_page` shows the status and the feedback form; the report is downloaded from Test Reports on the portal home `/my/home`, which the user menu's **My Account** opens. customer.md asks for no link on the order page, so the spec does not check one.
