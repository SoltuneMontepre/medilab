# WF-06 Report signing, release and delivery: connected journey plan

## Position

Story step 14. It starts when WF-05 approves the last outsourced result: that approval completes the test request, which creates the draft report and the Lab Head's signing task in the same transaction. SF-01 has already paid the order in full. The journey walks the main path with WF-06-A4: digital signing stays disabled, as in the demo data. The delivery method is the one the app gives every order's request, in person (finding 3), so the delivery is WF-06-A1, the main path's `Deliver by e-mail? no` branch, not the e-mail delivery: sample delivery staff hand the report over and record the delivery, which sends no e-mail. The report language is bilingual for the same reason (WF-06-A2), which changes no step. The Lab Head's and the customer's notices go by e-mail, their default, and are outside the browser. SF-03 later sends a replacement report through this flow again.

## Connection findings

1. **The local ONLYOFFICE gateway refused Odoo's `POST /converter` until it was fixed in this work.**
2. **The PDF is prepared by a cron, not a click.** The draft report and the signing task are created on the last result approval; `ir_cron_test_report_prepare` ("Prepare test report PDFs", every minute) prepares the PDF, about 50 s after the Lab Head first opened the draft on the spare instance. A failed attempt is counted and retried later. The spec waits 90 s, opening the report again, then clicks **Prepare PDF**, which prepares synchronously.
3. **Orders always produce a bilingual report delivered in person.** `_confirm_order` calls `create_from_order` without `report_language` or `delivery_method` (`sale_order_confirmation.py:313-322`), so the defaults `bilingual` / `in_person` apply, as `overview.md` (Delivery) defines them: "bilingual by default", "in person by default". The chain therefore walks WF-06-A1 and WF-06-A2; the main path's e-mail delivery (`Deliver by e-mail? yes`, recording it e-mails the PDF) is reached only when Sales sets e-mail on the test request, which no step of WF-01's main path does.
4. **What "withheld for payment" blocks (SF-01 ↔ WF-06).** While the order is not paid in full, not on credit and not free, the report is issued but not offered in the portal, **Record Delivery** in Reports to Deliver is refused with "{REPORT} is sent once order {ORDER} is paid in full.", and the notice says it is released once paid. A late payment sends no new notice. The journey's order is paid in full by SF-01, so none of this applies.
5. **The candidate is frozen to the printed business data.** If the customer profile or a result changes between review and approval, the PDF stops being current, **Sign** disappears and a new PDF is prepared.
6. **The Lab Head is not notified.** The draft creates the role task "Ký phiếu kết quả: Draft report of `{REQUEST}`" in the Department Queue (its name keeps the Vietnamese task type even on English screens) and no message. business-flows.md says the Lab Head is notified. The task closes on approval; signing happens on the report form. The chain marks the notice outside the browser, by e-mail, the Lab Head's default channel, although the app sends no e-mail for it either; the Lab Head then works from the task.
7. **The customer sees the order Completed from the last result approval.** The portal badge maps the request status `completed` to Completed (`sale_order_customer.py`, `REQUEST_STATUS_TO_CUSTOMER`), as customer.md defines it ("All samples completed"), while Sales' `order_status` stays confirmed until issue, as business-flows.md requires ("order completed only on issue"). The chain checks only Sales's status after issue. The completed-looking page still offers **Request cancellation**, since that follows `order_status`.
8. **The customer is told the results are ready by e-mail unless they choose the portal.** Issue raises `result.released` on the order to its contact. The event is not mandatory, so with a new customer's defaults it goes by e-mail (step 7, outside); it reaches the portal list only once the customer ticks **In the portal** for "Results released", titled with the report number: "The results of order `{ORDER}` are ready. Download report `{REPORT}` from your portal." On this stack the e-mail cannot be sent: SMTP fails, and the retries of the mandatory payment receipt mark the contact's address bounced, after which no e-mail is queued.
9. **The accredited nitrate test gets no mark on the report.** SF-06 made the journey's nitrate test accredited (`is_accredited` is true), but the report prints only the quality registrations' marks (`quality_registration.py:41`, such as `(*)` after a registered parameter). The PDF prints "`Journey nitrate {TAG}` 12,50 mg/L LAB-CR6-01" with nothing after the name. business-flows.md SF-06: "reports carry the accredited and registered marks". An observation the chain no longer checks.
10. **The order page has no report link.** `sol_commerce.order_page` shows the status and the feedback form; the report is downloaded from Test Reports on the portal home `/my/home`, which the user menu's **My Account** opens. customer.md asks for no link on the order page; an observation the chain does not check.
11. **Order status before issue.** Before issue Sales's `order_status` is confirmed, and the request reads Completed; after issue the request reads Reported and the order completed. Only the state after issue is a step of the path.
12. **The issued report's samples read Retained.** The delivery step reads it on the report's Samples tab for SF-04, which starts from it.
13. **Whether Sales can still change `report_language` / `delivery_method` on a paid test request** was not checked on the live app.
