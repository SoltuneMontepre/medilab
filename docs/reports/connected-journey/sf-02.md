# SF-02 Order cancellation: connected journey plan

## Position

Last step of the story (step 18). SF-02 starts from a confirmed order that is not completed, which the story obtains by WF-01-A3: the customer `Journey Foods {TAG}` reorders the journey order that WF-06 completed, and the reorder goes through WF-01's main path to a confirmed order: Sales claims it, sets the agreed pickup day and sends the quotation with a 30 % advance, which the customer pays by bank transfer (WF-01-A4, since the stack has no PayOS); the balance due stays at the dialog's default and no priority is asked. Then the SF-02 main path: the customer requests cancellation with a reason on the portal, Sales accepts, and the order and its test request are cancelled. SF-02-A1..A5 are not walked.

## Connection findings

1. **Accepting the cancellation does not cancel the test request.** Confirmed on the live app: after Sales accepts, the order is cancelled while its test request keeps its status (`confirmed` with the default balance due, `Paid` when the balance is due before the report) and its sample stays `Expected`. `_cancel_order` calls `_cancel_laboratory_documents` (`sol_commerce/models/orders/sale_order.py:423`), whose body is empty ("once that model exists", `sale_order.py:432-433`), and nothing overrides it. This breaks the SF-02 main path "the order and its test request are cancelled" and the F-11 rule "Accepting cancels the order and everything under it"; the unit test checks only the order (`sol_commerce/tests/test_order_cancellation.py:45-55`). The spec fails there. Staff can still cancel the test request by hand (sample delivery staff: `button[name=action_cancel]`, which cancels its sample, `test_request.py:242-245`), a repair the journey does not make.
2. **No Cypress spec for SF-02.** `src/tests/cypress/e2e/flows/sf-02-order-cancellation/` is empty although `src/tests/cypress/e2e/README.md:82` lists `order-cancellation.cy.js`. The journey is the first click-through of the cancellation request.
3. **Reorder lines have no sample type.** Confirmed: the cart shows `Choose a sample type` on both lines; `action_reorder` copies product and quantity only (`sale_order.py:458-481`). It also drops the requested date, the priority and the pickup day. WF-01-A3 in `customer.md:178` reads as if the draft were ready to submit.
4. **SF-02-A4 is not built.** For an order with a collected sample, accepting is refused with a message naming a change request the Head of Sales approves (`sale_order.py:448-454`), but no such change request exists in `sol_commerce`. The journey avoids it by receiving no sample for the reorder.
5. **Accepting is refused while a payment waits for the accountant** (`_check_no_pending_collection`, `sol_commerce/models/invoicing/sale_order.py:232-234`), but sending the request is not, although `customer.md:219` says "A cancellation is refused while a payment awaits the accountant". Not tried: the journey confirms the advance first.
6. **SF-04-A2 has nothing to dispose of.** The sample of `{REQUEST}` never arrived, yet `_disposal_allowed` accepts any cancelled sample (`sol_laboratory/models/sample_collection/sample.py:578-584`), so a disposal could be recorded for a sample the laboratory never held. business-flows.md SF-04-A2 does not say whether a never-received sample is disposed of.
7. **Customer sees the raw request status.** Confirmed: the portal box reads `Cancellation: requested` / `Cancellation: accepted` (`catalog_templates.xml:349`), not the labels. The decision notice is a chatter message on the order, which the portal order page does not show.
8. **Cancellation task goes to the order's salesperson only.** Confirmed: the task is in `demo.sales`'s My Tasks because `demo.sales` claimed the reorder (`cancellation_request.py:100-108`); its row opens the cancellation request itself.
9. **Sales types the pickup day again.** The quotation cannot be sent without `expected_collection_date`, which the reorder does not copy; Send quotation stops with "Missing required fields".
10. **The reorder's test request is not paid.** A portal order's balance due defaults to before sample collection (`sale_order.py:226`) and the Send quotation dialog keeps it, so confirming the reorder after its verified advance leaves the test request `confirmed`, not paid, against the WF-01 main path ([WF-01](wf-01.md)). SF-02 starts from a confirmed order, so the flow goes on.
