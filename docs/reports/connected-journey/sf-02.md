# SF-02 Order cancellation: connected journey plan

## Position

Last step of the story (step 18). The customer `Journey Foods {TAG}` reorders the journey order that WF-06 completed (WF-01-A3), and the reorder goes through WF-01 again on its main path with the cash advance of WF-01-A4, up to a confirmed order with a paid test request and no sample received. Then the SF-02 main path: the customer requests cancellation with a reason on the portal, Sales accepts, and the order is cancelled. The test request is not cancelled by the acceptance (finding 1), so the journey adds a Sales click on the test request's Cancel button to reach the state SF-02 promises. SF-02-A1 (the customer cancels the reorder before confirmation) is the fallback if the confirmed path cannot be clicked. SF-02-A2..A5 are not walked.

## Connection findings

1. **Accepting the cancellation does not cancel the test request.** `_cancel_order` calls `_cancel_laboratory_documents` (`sol_commerce/models/orders/sale_order.py:423`), whose body is empty with the docstring "once that model exists" (`sale_order.py:432-433`), and nothing overrides it in any module. The test request stays Paid, its expected samples stay Expected, and their open sample collection tasks stay open for sample delivery staff. The customer badge reads Cancelled only because the order status wins (`sale_order_customer.py:86`). This breaks the SF-02 result "the order and its test request are cancelled" and the F-11 rule "Accepting cancels the order and everything under it". The unit test checks only the order (`sol_commerce/tests/test_order_cancellation.py:45-55`). Workaround by clicks: step 15, Sales cancels the test request on its form (`test_request_views.xml:57-65`; Sales may, `role.xml:14`).
2. **No Cypress spec for SF-02.** `src/tests/cypress/e2e/flows/sf-02-order-cancellation/` is empty although `src/tests/cypress/e2e/README.md:82` lists `order-cancellation.cy.js`; no other spec touches cancellation requests. The only reorder evidence is TC-WF01-A3, which opens the order by a direct URL and checks the reorder over RPC (`wf-01-order-to-test-request/order-to-test-request.cy.js:163-185`). F-11 is not marked done (`docs/reports/feature-list/readme.md:41`). Every SF-02 handle in this plan comes from the templates and views, not from a passing test.
3. **Reorder lines have no sample type.** `action_reorder` copies product and quantity only and does not call `_preselect_sample_type` (`sale_order.py:458-481`; the cart's add does, `sale_order.py:341`). The customer must pick each sample type in the cart (step 2), or Sales must, before the quotation can be sent (`sale_order.py:586-590`). It also drops the requested date and priority of SF-07. WF-01-A3 in `customer.md:178` reads as if the draft were ready to submit.
4. **SF-02-A4 is not built.** For an order with a collected sample, accepting is refused with a message naming a change request the Head of Sales approves (`sale_order.py:448-454`), but no such change request exists in `sol_commerce`. The journey avoids it by receiving no sample for the reorder. If WF-02 is ever run on the reorder, steps 13 and 15 change: step 13 is refused.
5. **Accepting is refused while a payment waits for the accountant** (`_check_no_pending_collection`, `sol_commerce/models/invoicing/sale_order.py:232-234`), but sending the request is not, although `customer.md:219` says "A cancellation is refused while a payment awaits the accountant". Step 8 must be done before step 13.
6. **SF-04-A2 has nothing to dispose of.** The samples of `{REQUEST}` never arrived (`received_at` empty), yet `_disposal_allowed` accepts any cancelled sample (`sol_laboratory/models/sample_collection/sample.py:578-584`), so a disposal could be recorded for a sample the laboratory never held. business-flows.md SF-04-A2 does not say whether a never-received sample is disposed of; a question for the owner (`questions/` topic of SF-04). The story step "SF-04-A2 disposal of nothing/its sample if any" should end at "no sample".
7. **Customer sees the raw request status.** The portal box prints `cancellation.status` (`catalog_templates.xml:349`), so the customer reads `requested`/`accepted`, not the labels; assert on those strings. The decision notice is a chatter message on the order (`cancellation_request.py:148-158`), which the portal order page does not show; e-mail delivery is outside the journey.
8. **Cancellation task goes to the order's salesperson only.** `_create_task` assigns the person of `order.user_id` (`cancellation_request.py:100-108`); the journey must claim the reorder as `demo.sales` (step 4) so the task appears in that user's `My tasks`. The menu path in step 12 works for any Sales user.
