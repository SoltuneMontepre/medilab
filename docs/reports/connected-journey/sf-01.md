# SF-01 Invoicing and payment collection: connected journey plan

## Position

Story step 13, between WF-05 (the sample completes, the test request is `completed`) and WF-06 (the report is approved, issued, delivered and downloaded). The journey collects the balance payment request that WF-01 created when Sales confirmed the order. It walks SF-01-A1 in two parts with non-online methods: part 1 is a bank transfer the customer reports on the portal, part 2 is SF-01-A2, cash that Sales records. The accountant confirms each part. Each confirmation posts its invoice and issues a receipt (main path). Then the customer downloads the invoices on the portal. PayOS is not reachable, so no part is paid online. SF-01-A3 and SF-01-E1 to E3 are not walked. Reconciliation (`a4`-`a7`) is shown read-only (finding 6).

## Connection findings

1. **The balance holds sample collection unless WF-01 changes Balance Due.** A portal order is created with `balance_due = before_collection` (`sol_commerce/models/orders/sale_order.py:226`). With that value, confirming the order leaves the test request `confirmed`, not `paid` (`_status_after_confirmation` → `_can_collect_samples`, `sol_commerce/models/orders/test_request.py:36-41`; `_collection_hold`, `sale_order_confirmation.py:225-242`). It also hides "Start sample collection" and refuses sample intake (`test_request.py:43-49`). Cypress TC-F10-02 asserts this hold (`src/tests/cypress/e2e/flows/wf-01-order-to-test-request/payment-and-confirmation.cy.js:40-54`). The docs say the opposite: there are two choices, "before the report" is the default, and the balance never holds collection (`docs/functional/ecommerce_module/features/sales.md:108`, `:200`, `:209`; `docs/specs/payment-requests.md:14`; business-flows WF-01 main path). Consequence: the story (WF-02 at step 6, SF-01 at step 13) connects only if WF-01, in the Send quotation dialog, sets `.modal .o_field_widget[name=balance_due]` to "Before the report" (or "At sample collection") (`sol_commerce/views/orders/quotation_send_views.xml:41`). Otherwise SF-01 must run between WF-01 and WF-02. This mismatch between the docs and the code needs an owner decision.
2. **A full advance leaves nothing for SF-01.** `_request_balance` makes no request when the order is already paid (`sale_order_confirmation.py:341-343`). The Balance Due field is hidden when `advance_mode == 'full'` (`quotation_send_views.xml:41`). WF-01 must choose a percentage or a fixed advance (Cypress uses 30 %). Otherwise SF-01 receives no balance request and WF-06 sees a paid order.
3. **No screen link to the payment receipt.** The receipt exists only at `/my/invoices/<invoice>/receipt/<payment>` (`sol_commerce/controllers/portal.py:119`). No portal template links to it: the invoice page, the order page and the notice page (`sol_commerce/views/notifications/portal_templates.xml:54-60`) have no such link. Cypress opens it with `cy.visit` using ids read over RPC (`payment-collection.cy.js:105`). `customer.md:235` ("download … the payment receipt") is not built for clicks. Click-only substitute: the "Payment of … was recorded." notice on `/my/notifications` (step 13). The receipt download is reported as missing.
4. **The order and its invoices are not linked on the portal.** The order page shows the balance request but no invoices. The header navigation has no Invoices entry (`navigation_templates.xml:23-30`). The customer reaches invoices only through `/my` → "Your Invoices" (Odoo `account.portal_invoice_client`), and the list does not name the order. The journey tells the invoices apart by amount.
5. **PayOS (SF-01-M, the online half of SF-01-A1, E4).** Online payment needs a signed PayOS webhook. Cypress forges it with `cy.task("payosNotify")` (`src/tests/cypress/e2e/flows/sf-01-payment-collection/setup.js:123-125`; plugin `src/tests/cypress/plugins/payos.js`), and the journey cannot do that by clicks. If the PayOS provider is published (`_portal_payos_available`, `sol_commerce/models/invoicing/account_move.py:199`), the PayOS button is visible. Clicking it only creates a link and calls PayOS (`sol_commerce/controllers/order.py:155-170`, `controllers/portal.py:61-82`); no payment results. The same applies to "Generate PayOS QR" in the Sales dialog (`payment_collection.py:212`). Substitute: a bank transfer reported on the portal plus cash recorded by Sales (steps 3-8). Both use the same accountant confirmation and the same invoice posting.
6. **Reconciliation (`a4`-`a7`, SF-01-E3) has no data to work on.** A reconciliation day matches PayOS `payment.transaction` rows, which only the gateway writes. Cypress creates them as administrator over RPC (`setup.js:144-170`). Days are unique (`reconciliation_day.py:62`), so locking today would also block a rerun on the same database. Click-only part: Accountant → E-commerce → Reconciliation (`sol_commerce.menu_reconciliation`, `/odoo/reconciliation-days`). Open the demo locked day, the one that holds `sol_demo.demo_account_move_payos_locked`, and check status Locked and that the Lock button is absent. Creating, posting missing payments and locking are not walked.
7. **The story order hides the report hold.** SF-01 runs before WF-06, so WF-06 never shows a withheld report. To show "the issued report reaches the customer only once paid in full", split SF-01: do steps 1-6 (part 1), then WF-06 up to issue, then steps 7-13. Between them, WF-06 sees the banner, no `action_record_delivery` button, the notice "…is released in your portal once the order is paid in full." and no report on `/my/test-reports`. After step 8 the report appears on the portal and the delivery button shows. No notice tells the customer that a withheld report has been released after payment (`_refresh_funding` only calls `_release_test_request`, `payment_request.py:104-113`), so the customer must go back to the portal on their own.
8. **The Record payment button has no stable handle.** Its `name` is the database id of `sol_commerce.action_payment_collection` (`sale_order_views.xml:138`). Cypress reads that id over RPC (`payment-collection.cy.js:153`). The journey selects it by text and position in the header.
9. **Credit customers are out of scope here.** The accountant's "create the final invoice" (`a1`-`a2`) applies only to customers on credit (`_credit_invoice_eligible`, `sale_order.py:270`). `Journey Foods {TAG}` has no sales terms, so it is not on credit. Cypress forces `status: completed` over RPC for that path (`setup.js:33-37`). Not walked.
