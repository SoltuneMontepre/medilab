# SF-03 Change request on a signed document: connected journey plan

## Position

Story step 15, between WF-06 (step 14, the journey report issued, delivered and downloaded) and SF-04 (step 16). The journey walks **SF-03-A1**: sample delivery staff raise a change request on the issued journey report, the Lab Head approves it in the test report change-request chain, the approval creates report version 2 as a draft with a fresh Lab Head signing task, and the replacement goes through WF-06 again (PDF preparation, Lab Head review and signature, issue as **WF-06-A4** because digital signing is off in the demo, delivery). Issuing it marks version 1 `replaced`; the customer's portal then lists only the replacement. The main path (tester's change request on a completed result) with **SF-03-A3** is a variant, not walked: on an issued report it needs two change requests, a WF-04 re-entry by the tester and a head approval before the replacement exists, so it costs a second pass through WF-03/WF-04 for the same end state. **SF-03-E1** (Lab Head rejects) is a variant that ends the flow without a replacement, so it cannot be walked on the journey record before A1.

## Connection findings

1. **The replacement's PDF cannot be prepared on this stack.** The ONLYOFFICE gateway refuses Odoo's `/converter` path (WF-06 finding 1), so the journey report v1 is never issued and this flow is skipped. On a demo report, version 2 stays a draft, **Prepare PDF** shows "ONLYOFFICE could not convert the document to PDF right now; prepare it again later." and version 1 stays issued and current.
2. **The PDF is prepared by a cron-triggered job.** Approving the change request opens the signing task and wakes `test_report.prepare`; the Lab Head's **Prepare PDF** runs the same preparation synchronously. Step 6 handles both.
3. **Only sample delivery staff can raise a change request on a report.** The button is grouped `group_permission_test_report_deliver_all`; in the demo only `demo_role_sample_delivery_staff` holds it. The Lab Head's form of an issued report shows only **Download PDF**. business-flows.md SF-03 names the trigger "a person who can edit a type of document, or deliver reports", but its diagram has only Tester, Head of department and Lab head lanes.
4. **Nobody tells the approver.** With in-app notices on, the Lab Head receives no notice when a change request is raised, and no task exists for it; only the requester is notified on approval or rejection (`change_request.approved/rejected`). The Lab Head must open Laboratory > Requests > Change Requests. Soft checks, red.
5. **The report change request changes no data.** `_new_version` creates a new draft from the current business records; the typed change is only the signing task's note. The replacement prints what v1 printed unless a record was corrected through its own workflow. The journey checks the version chain, the new number and the portal.
6. **The replacement takes a new report number.** Version 2 has no number until its PDF is prepared and then reserves the next one. Later flows look the report up by the request code.
7. **Cypress reaches this state by RPC and demo records only.** No Cypress spec carries a replacement through PDF, signature and issue; steps 7-12 have no browser evidence on this stack.
8. **The change-request chain differs from SH-07.** SH-07 gives the Head of Department as the approver of a result change request; the demo chain `demo_approval_chain_test_result_change_request` has only the Lab Head. Not on the A1 path.
9. **No way to take back the approval.** A run that fails after step 4 leaves an applied change request and a draft version 2; a rerun on the same database needs the instance reset (one open replacement per report).
