# SF-03 Change request on a signed document: connected journey plan

## Position

Story step 15, between WF-06 (step 14, the journey report issued, delivered and downloaded) and SF-04 (step 16). The journey walks the **main path**: the tester raises a change request on the completed nitrate result, the change-request chain signs it, and a new version replaces the old one, which stays readable. The result is printed on the issued report, so **SF-03-A3** applies by itself: raising the correction creates the report's change request, which waits for its approval and for the corrected result's approval, then prepares the replacement draft with a fresh signing task; the replacement goes through WF-06 again (PDF, Lab Head review, approval as **WF-06-A4**, issue, delivery as **WF-06-A1**) and issuing it marks version 1 `replaced`. No other path is walked.

## Connection findings

1. **The result's change-request chain is the Lab Head's, not the head of department's.** SH-07 (`shared.md:150`) names the Head of Department as the approver of a result change request, and the SF-03 diagram puts "[result] Approve the change request?" in the head of department's lane; the demo chain `demo_approval_chain_test_result_change_request` has only a Lab Head level. The chain walks the configured chain ("the change-request chain signs it").
2. **The approver is told by a notice, not a task.** Raising a change request, and each level it then waits for, raises the mandatory `change_request.waiting` to the people who can sign that level, except the one who acted (`sol_laboratory/models/testing/change_request.py`); no task exists for it. The Lab Head opens Laboratory > Requests > Change Requests.
3. **The report change request is a second request the Lab Head signs.** The correction creates it with the text "Replace the report with the corrected result …" (`test_report_issue.py` `_correction_request`). Approved before the corrected result, it stays Approved and is applied when the head approves the result (`_follow_corrections`).
4. **The corrected version cannot be edited from the sample test.** Approving the result change request copies the result as version 2, Draft, puts the test back in Testing and opens a testing task in the Chemistry queue, unassigned, with the change as its note. The sample test's Results tab opens version 2 in a read-only dialog; the tester edits it from Test Results.
5. **The PDF is prepared by a cron-triggered job**, as in WF-06; the Lab Head's **Prepare PDF** runs the same preparation.
6. **The replacement takes a new report number.** Version 2 reserves the next number when its PDF is prepared.
7. **The customer is told of the replacement by e-mail**, like the first report (WF-06 finding 8).
8. **A report change request by sample delivery staff (SF-03-A1) works.** Walked by the earlier journey: **Request a Change** on the issued report, the Lab Head's approval creates version 2 with a fresh signing task, and WF-06 issues it. Only `demo_role_sample_delivery_staff` holds the deliver permission, so only it sees the button on a report.
9. **No way to take back an approval.** A run that fails after step 3 leaves an applied change request; a rerun on the same database needs the instance reset.
