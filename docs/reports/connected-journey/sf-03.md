# SF-03 Change request on a signed document: connected journey plan

## Position

Story step 15, between WF-06 (step 14, the journey report issued, delivered and downloaded) and SF-04 (step 16). The journey walks **SF-03-A1**: sample delivery staff raise a change request on the issued journey report, the Lab Head approves it in the test report change-request chain, the approval creates report version 2 as a draft with a fresh Lab Head signing task, and the replacement goes through WF-06 again (PDF preparation, Lab Head review and signature, issue as **WF-06-A4** because digital signing is off in the demo, delivery). Issuing it marks version 1 `replaced`; the customer's portal then lists only the replacement. The main path (tester's change request on a completed result) with **SF-03-A3** is a variant, not walked: on an issued report it needs two change requests, a WF-04 re-entry by the tester and a head approval before the replacement exists, so it costs a second pass through WF-03/WF-04 for the same end state. **SF-03-E1** (Lab Head rejects) is a variant that ends the flow without a replacement, so it cannot be walked on the journey record before A1.

## Connection findings

1. **PDF preparation of the replacement needs ONLYOFFICE and the laboratory bucket.** `_prepare_pdf` refuses while `_check_editing_available` fails (test_report_preparation.py:169) and `_convert` asks ONLYOFFICE to convert the DOCX (test_report_candidate.py:123-134); the scheduled job only waits during an outage (test_report_scheduled_job.py). Without them steps 10-16 cannot happen: v2 stays draft, v1 stays issued and current, the portal keeps v1. The same dependency already gates WF-06 step 14, so if WF-06 issued v1 by clicks, SF-03 works in the same environment. Cypress never prepares or signs a new report for this reason (wf-06 setup.js:86-88, 142-145; sf-03 setup.js:149-150). No click-only fallback exists: run the journey on a `task setup` environment with managed ONLYOFFICE up (`task onlyoffice:status`); otherwise stop SF-03 after step 8 and record v2 as "draft waiting for its PDF", handing SF-04/SF-09 an issued v1.
2. **The PDF is prepared by a cron-triggered job.** `_open_signing_task` triggers the `test_report.prepare` cron (test_report.py:241-248). If the cron runner does not pick it up in time, the Lab Head clicks **Prepare PDF** (shown when `pdf_preparable` and no current candidate, test_report_views.xml:105-111), which runs the same preparation synchronously. Step 10 must handle both.
3. **Only sample delivery staff can raise a change request on a report.** The button is grouped `group_permission_test_report_deliver_all` and `_raise` checks the `deliver` permission (`_change_request_action`, test_report.py:258-260); in the demo only `demo_role_sample_delivery_staff` holds it. Tester, head of department and Lab Head see no **Request a Change** on a report. business-flows.md SF-03 lists only Tester, Head of department and Lab head as actors, which does not match (the overview's "anyone who can deliver reports" rule does).
4. **Nobody tells the approver.** Raising creates no task and no notification for the Lab Head; only the requester is notified on approval/rejection (change_request.py:177-200, 226-238; events `change_request.approved/rejected` only). The Lab Head must go to Laboratory → Requests → Change Requests and filter Requested (step 5). The journey cannot use a to-do link here.
5. **The report change request changes no data.** `_new_version` creates a new draft from the current business records (test_report.py:266-280); the typed change is only the signing-task note. The replacement prints what v1 printed unless a record was corrected through its own workflow before. The journey therefore checks the version chain, the new number and the portal, not changed content. A content change by clicks needs the main path / SF-03-A3 (correct a result).
6. **The replacement takes a new report number.** v2 has no `code` until its PDF is prepared and then reserves the next sequence number (`_prepare_candidate`, test_report_preparation.py:234-261); TC-SF03-A1 asserts `code` false on the draft. SF-04/SF-09 must look up the report by request code, not by `{REPORT_V1}`.
7. **Cypress reaches this state by RPC and demo records only.** TC-SF03-A1 and WF-06 `replacementOf` use the demo report `sol_demo.demo_test_report_by_email` and raise the request through `medilab.change.request.raise` `create`/`action_raise` over RPC (report-release.cy.js:62-84); no spec carries a replacement through PDF, signature and issue. Steps 9-16 have no browser evidence; plan them from the code.
8. **Change-request chain differs from SH-07.** SH-07 (shared.md:150) gives the Head of Department as the change-request approver for a test result; the demo chain `demo_approval_chain_test_result_change_request` has only the Lab Head (approval_level.xml:39-45). Not on the A1 path, but the main-path variant is signed by the Lab Head, not the head.
9. **Delivery depends on the request's delivery method.** If the journey request is delivered by e-mail, Record Delivery refuses a recipient without an e-mail or with a bounced one (test_report.py:205-207) and sends an e-mail with the PDF (needs no mail server to record, the message is stored). Use the same method WF-06 used for v1.
10. **No way to take back the approval.** Approval is final (`_approval_process_completed` for decided statuses), so a run that fails after step 6 leaves an applied request; a rerun on the same database needs a new journey test request (one open replacement per report, `_change_request_open`, test_report.py:262-264).
