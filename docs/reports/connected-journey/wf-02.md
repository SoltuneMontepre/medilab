# WF-02 Sample reception and handover: connected journey plan

## Position

Story step 6, between WF-01/SF-07 (confirmed portal order, advance verified, test request `paid`, tests urgent) and SF-11 / WF-03 (folders and assignment on the received sample). The journey walks the WF-02 main path: the customer brings the one sample; sample delivery staff record the actual handover against the expected samples, the condition, receipt and storage, have the customer sign, print the label; the head of department scans the label. WF-02-A3 does not apply when both tests belong to Chemistry (see Hands over); no exception path is walked.

Both tests land in the same queue, Chemistry, provided SF-08 gives `Journey nitrate {TAG}` an in-house way whose `department_id` is Chemistry (`sol_demo.demo_hr_department_chemistry`). A test goes to the department of its accepted way, or of the default way for the sample type when the accepted way is subcontracted (`_department_by_test`, `sol_laboratory/models/sample_collection/sample.py:628`): lead on bottled water defaults to `demo_parameter_method_lead_aas` (Chemistry) whatever way WF-01 accepted. Chemistry therefore gets one department handover and one scan. Chemistry must then: assign and book the nitrate task (WF-03), and outsource the lead task (WF-05). If SF-08 picks a Microbiology method, a second handover row appears and `demo.microbiology_tester` must also scan (WF-02-A3).

## Connection findings

1. The customer's signature cannot be given in a browser. The handover record form has no signature widget or Sign button (`sol_laboratory/views/sample_collection/handover_record_views.xml:22-74`); `write` refuses signing fields with "A handover record is signed only by the customer, on the mobile app." (`sol_laboratory/models/sample_collection/handover_record.py:98-99`); the portal has no handover screen. Signing is only `POST /medilab/api/v1/handover-records/<id>/sign` with a phone key (`controllers/laboratory_api_handover_records.py:23`); Cypress uses `action_sign` over RPC (`sample-reception.cy.js:284`). Consequence: click-only, the record stays Draft. Nothing downstream checks it (only `sample_returns.py:45` reads its status for extras), so the journey continues. Nearest path: Playwright `request` context does the phone sign-in + sign calls as the "phone", labelled as a non-click step; signing also renders a PDF (wkhtmltopdf) and e-mails the customer.
2. Test requests cannot be found by order number while E-commerce is installed: `order_number` is written only by the uninstall hook (`sol_commerce/hooks.py:32`, `sale_order_confirmation.py:385-388`), though the search view offers it (`test_request_views.xml:177`). Search by Customer instead; WF-01 must hand over the customer name, and the run tag keeps it unique.
3. A portal order defaults to `balance_due = before_collection` (`sol_commerce/models/orders/sale_order.py:226`). With only the advance paid, the test request stays `confirmed`, not `paid` (`orders/test_request.py:42`), and receipt is refused with "Verify the order balance before collecting its samples." (`sale_order_confirmation.py:240`). WF-01 must set Balance Due to "Before the report" in the send-quotation wizard (`.o_field_widget[name=balance_due]`, `views/orders/quotation_send_views.xml:41`), which also suits SF-01 collecting the balance later. Otherwise WF-02 cannot start.
4. Print Labels returns a `qweb-pdf` report (`test_request.py:247-249`, `sample_label_report.xml`): the browser gets a PDF download, needing wkhtmltopdf in the container. Playwright must accept downloads; the label's content (lab code, request code, Due date, QR) is checkable only by opening the PDF or `/report/html/sol_laboratory.report_sample_label/<id>`, which is a direct URL.
5. No to-do or notification tells sample delivery staff that a paid request expects its sample (no such event in `sol_laboratory/constants/notifications.py`); finding it is a list search. A collection task exists only for WF-02-A1 (Sales "start sample collection").
6. The order of business-flows.md (receipt → customer signs → print label → hand over) is not enforced: receipt, handover record and labels are independent; the department handover row is created at receipt, not after signing or printing (`sample.py:383-397`, `_open_testing_work` `sample.py:592`). Testing tasks are created at receipt, before the scan; the scan only records the department's receipt, which makes the tests bookable and runs the department plan (`sample_handover.py:79-109`). So "testing tasks wait in the queue" is true before the head scans; WF-03 must start after step 12, or booking is refused with "... waits until its department receives its sample."
7. The scan dialog reopens itself after each success (`sample_scan.py:24-37`, `params.next`); the spec must close it before navigating.
