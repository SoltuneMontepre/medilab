# SF-07 Result dates and priority orders: connected journey plan

## Position

Story step 5, carried out inside WF-01 on the journey's own order, with one optional step after WF-02. The journey walks
the SF-07 main path (standard turnaround and estimated return date shown on the draft quotation), SF-07-A1 (the
customer asks for priority with a requested date on the portal cart; Sales checks feasibility and accepts it before
sending; the accepted priority makes the test request's tests urgent) and, optionally, SF-07-A3 (the head of
department changes the journey parameter's internal due date with a reason). SF-07-E2 is the fallback when Accept
priority reports the date infeasible. SF-07-A2, SF-07-E1 and the "Change return date" wizard are not walked.

The slots WF-01 must leave, by WF-01 state:

| SF-07 step | WF-01 state before | WF-01 state after |
| ---------- | ------------------ | ----------------- |
| C1 requested date + priority on the cart | cart: order `order_status=draft`, `state=draft`, lines with sample type and way chosen | same cart; WF-01 then clicks Submit, order `submitted` |
| S1-S4 turnaround, estimate, Accept priority | order `claimed`, `state=draft`, ways and expected samples confirmed, `expected_collection_date` typed and saved | still `claimed`/`draft`, `priority_request=accepted`; WF-01 then clicks Send quotation |
| C2 dates on the portal quotation | quotation sent (`state=sent`) | unchanged; WF-01 customer accepts and pays |
| L1-L2 priority on the test request and its tests | order `confirmed`, test request `paid` | unchanged |
| H1-H3 internal due date override (optional) | after WF-02: sample received, label scanned, tests `waiting` | test keeps `due_date_reason`; WF-03 continues |

## Data

- `TODAY`: the date in Asia/Ho_Chi_Minh when the journey runs.
- `PICKUP` (typed by WF-01 in `expected_collection_date`): the next working day after TODAY.
- `REQUESTED`: TODAY + 14 calendar days, moved forward to a Monday-Friday that is not a public holiday of the company
  calendar (from 2026-11-26: 2026-12-10). Far enough that the priority payment deadline (REQUESTED − N working days)
  is later than the default 3-day deadline and the WF-02 collection appointment on PICKUP passes the turnaround check.
- `N`: the max `turnaround_days` of the two ways (SF-08 value for the journey way, demo value for the other,
  `sol_demo/data/sol_laboratory/parameter_method.xml`).
- `DUE_AUTO`: 23:59:59 local of the working day before REQUESTED (safety margin default 1,
  `sol_laboratory/constants/settings.py:4`).
- `DUE_OVERRIDE`: 10:00:00 local, 2 working days before DUE_AUTO (2026-12-07 for the date above), typed in the head's
  language format (vi: `dd/MM/yyyy HH:mm:ss`; verify).
- `REASON`: `Journey {TAG}: hoàn thành sớm để dự phòng sự cố máy.`
- Demo records: `sol_demo.demo_res_users_sales`, `sol_demo.demo_res_users_head_of_department`,
  `sol_demo.demo_hr_department_chemistry` (head = demo head, tester = `demo.tester` in Chemistry,
  `person.xml:28-31`).

## Connection findings

1. Receipt does not fix the expected return date on the order path. `_compute_committed_date`
   (`sol_commerce/models/orders/sale_order_dates.py:114-120`) fills `committed_date` with the estimate whenever the
   order has a turnaround, it is frozen at send and copied to the test request at confirm
   (`sale_order_confirmation.py:317`). `_commit_on_receipt` (`sol_laboratory/models/sample_collection/test_request_estimate.py:122-138`,
   called from `sample.py:395`) only acts on requests with no `committed_date`. So WF-02 must check that
   "Ngày Trả Kết Quả Dự Kiến" (`committed_date`) on the test request form and the portal order page is UNCHANGED
   (= REQUESTED) after receipt. The business-flows main path ("otherwise receiving the first sample fixes the expected
   return date") only holds for requests created without an order. Mismatch to raise with the owner.
2. The customer can ask for priority only on the cart, before Submit. There is no portal control after submission
   (`/cart/save` and `/cart/submit` are the only callers of `_set_portal_dates`, `controllers/catalog.py:115-131`), and
   Sales cannot enter a requested date on an order without one: `requested_date` is `invisible="not requested_date"`
   and `priority_request` is a read-only badge (`sale_order_views.xml:300-301`). That is why Cypress TC-SF07-M/A1 write
   them by RPC (`priority-order.cy.js:49,64-67`). WF-01's planner must put C1 before its Submit click, or the A1 path is
   lost for the journey.
3. Accept priority needs an in-house slot within 30 days for every way, or it fails with "cannot be checked"
   (`test_request_estimate.py:64-82,113`, `strict=True`). `_place_way` (`test_request_simulation.py:127-170`) needs, for
   the journey way: a parameter authorization of a person in the way's department (SF-08: demo tester, Chemistry), a
   machine linked to the method with a duration or a way duration, and free working hours. A subcontracted way without
   a turnaround also blocks the check (`test_request_estimate.py:106-112`). SF-08 must deliver all of this before step 4.
4. SF-08 must fill `turnaround_days` ("Turnaround (working days)") on the new way, on the parameter's "Ways of
   Testing" list (`test_parameter_views.xml:47`) or the way form (`parameter_method_views.xml:22`). Without it: no
   "Results within…" on the cart, the order shows "No standard turnaround yet: <way>" and Send quotation is refused
   (`sale_order_dates.py:203-211`), and the estimate/committed date stays empty.
5. The priority check ignores the standard turnaround (`_earliest_return(..., 0, urgent=True)`,
   `test_request_estimate.py:113`) but the send and collection checks use it: a priority date earlier than
   pickup + N working days can be accepted and then block sending ("The advance would have to be paid before now…",
   `sale_order_dates.py:216-224`) or WF-02's Start sample collection (`sale_order_confirmation.py:465-485`). The
   journey avoids this with REQUESTED = TODAY + 14 days, so priority is accepted for a date later than the estimate:
   the tests still become urgent, but the "earlier than standard" promise is not exercised.
6. Sales must save `expected_collection_date` before S5: it is `required="1"` (`sale_order_views.xml:320`), so the
   save triggered by Accept priority fails while it is empty. WF-01's Cypress sets it by RPC
   (`order-to-test-request.cy.js:62`); the journey types it in the form.
7. Accepted priority makes every test of the request urgent through the computed `priority`
   (`sample_test_priority.py:64-70`), not through `marked_urgent`. SF-10's "mark urgent" button stays visible and only
   adds a reason; SF-10 should not expect a class change on the journey's tests.
8. SF-07-A3 timing: Change Due Date shows only for statuses waiting/assigned/testing/outsourced and only to the head
   of the testing department (`sample_test_due_date.py:119-123`, `sample_test.py:35-39`). An override earlier than
   DUE_AUTO narrows later SF-05/SF-10 moves; a move past it is held back (SF-10-E2) and could keep the booking on the
   repaired machine. Keep DUE_OVERRIDE well after the WF-03/SF-05 dates, or skip A3 if SF-05 cannot reschedule.
9. Cypress uses RPC throughout this flow: orders at `claimed` from `orderAt` (`wf-01-order-to-test-request/setup.js`),
   a lab-created request for A3 (`sf-07-priority-order/setup.js:15-44`), and user language switching to English
   (`setup.js:51-63`). No timers, crons or external services are involved in SF-07.
