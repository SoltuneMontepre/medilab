# SF-07 Result dates and priority orders: connected journey plan

## Position

Story step 5, carried out inside WF-01 on the journey's own order, with one optional step after WF-02. The steps inside
WF-01 are named `SF-07: …` in the spec `src/tests/playwright/journey/04-wf-01-sf-07-order-to-test-request.spec.js`.
The journey walks the SF-07 main path (standard turnaround and estimated return date shown on the draft quotation) and
SF-07-A1 as far as the screens go: the customer asks for priority with a requested date on the portal cart, Sales
presses Accept priority, the feasibility check ends in a server error (finding 1), and Sales declines. The request
therefore carries no priority and its tests are not urgent. SF-07-A3 (the head of department changes the journey
parameter's internal due date with a reason) stays optional, after WF-02. SF-07-A2, SF-07-E1, SF-07-E2 and the "Change
return date" wizard are not walked.

The slots WF-01 leaves, by WF-01 state:

| ---------- | ------------------ | ----------------- |
| C0-C1 turnaround, requested date + priority on the cart | cart with both lines, sample type and way chosen | same cart; WF-01 then clicks Submit, order submitted |

## Data

- `TODAY`: the date in Asia/Ho_Chi_Minh when the journey runs.
- `PICKUP` (typed by WF-01 in `expected_collection_date`): the next day from Monday to Friday after TODAY.
- `REQUESTED`: TODAY + 14 calendar days, moved to Monday when that is a Saturday or Sunday.
- `ESTIMATE`: read from the order form. In the run of 27 November 2026: first estimate 2 December, ESTIMATE 3 December
  for PICKUP 30 November, REQUESTED 11 December.
- Turnaround: 3 working days, the journey way's; Lead's ISO 17294-2:2016 way has 1.
- `DUE_OVERRIDE` (optional A3): 10:00, two working days before the automatic due date, typed in the head's date format.
- `REASON`: `Journey {TAG}: hoàn thành sớm để dự phòng sự cố máy.`

## Connection findings

1. **Accept priority ends in a server error, so no priority request can be accepted.** Pressing Chấp nhận ưu tiên on
   the order raises `ValueError: Field has no SQL representation because it is not stored in condition ('priority',
   'in', OrderedSet(['urgent']))`. The feasibility check searches the proposed bookings by `sample_test_id.priority`
   (`sol_laboratory/models/sample_collection/test_request_simulation.py`, `_held_bookings`, when `urgent`), and that
   field is computed without being stored or searchable (`sol_laboratory/models/testing/sample_test_priority.py`). The
   error does not depend on the order or the laboratory's load: every check for an urgent order builds that search.
   The module tests replace `_check_priority`, and Cypress TC-SF07-A1 only declines, so nothing walks the real check.
   Consequences for the story: the accepted branch of SF-07-A1, the requested date becoming the expected return date,
   urgent tests from an accepted priority and SF-07-E2 cannot be reached by clicks. The journey shows the error and
   declines; restore the accepted priority in the spec once the check answers.
2. Receipt does not fix the expected return date on the order path. The order has an expected return date from the
   moment it is submitted, it is kept when the quotation is sent and copied to the test request at confirmation, so
   the business-flows main path ("otherwise receiving the first sample fixes the expected return date") only holds
   for requests created without an order. WF-02 checks that the Expected Return Date is unchanged after receipt.
3. The expected return date is the laboratory's estimate, not the requested date. The customer asked for 11 December,
   the estimate from the pickup day was 3 December, and 3 December stayed the expected return date on the order, the
   portal and the test request, with the requested date shown beside it. The estimate itself moved once, from the
   first estimate counted from the day of submitting to the one counted from the pickup day Sales typed.
4. The customer can ask for priority only on the cart, before Submit. The portal order page has no control for it
   after submission, and the order form is defined to show the requested date and the priority badge only when they
   are set (`sale_order_views.xml`), so Sales cannot add them to an order that has none.
5. Sales must give the expected pickup day before deciding on the priority: the field is required and the form marks
   it invalid until it is filled.
6. SF-07-A3 timing: Change Due Date shows only for statuses waiting, assigned, testing and outsourced and only to the
   head of the testing department (`sample_test_due_date.py:119-123`). An override earlier than the automatic due
   date narrows later SF-05/SF-10 moves; keep DUE_OVERRIDE well after the WF-03/SF-05 dates, or skip A3 if SF-05
   cannot reschedule.
7. Cypress uses RPC throughout this flow: orders at `claimed`, a lab-created request for A3 and the requested date and
   priority request written on the order. No timers, crons or external services are involved in SF-07.
