# SF-07 Result dates and priority orders: connected journey plan

## Position

Story step 5. The SF-07 main path is part of preparing the quotation, so it runs inside WF-01 on the journey's own
order; its steps are named `SF-07: …` in `src/tests/playwright/journey/04-wf-01-order-to-test-request.spec.js`. The
customer reads the standard turnaround on the cart and gives the date they want the results, without asking for
priority (customer.md, Requested date); Sales sees the turnaround and the estimated return date from the agreed pickup
day beside the requested date on the quotation, and the customer reads them on the portal quotation.

**SF-07-A1** (priority request) is a test of its own, `src/tests/playwright/journey/04a-sf-07-priority-request.spec.js`,
right after WF-01: the journey's customer puts a new cart with the journey parameter, asks for priority with a date and
submits; Sales claims it, sets the pickup day and accepts the priority. It hands over nothing the chain uses. SF-07-A2,
SF-07-A3, SF-07-E1, SF-07-E2 and the "Change return date" wizard are not walked.

## Data

- `TODAY`: the date in Asia/Ho_Chi_Minh when the journey runs.
- `PICKUP`: the next day from Monday to Friday after TODAY.
- `REQUESTED` (main path): TODAY + 14 calendar days, moved to Monday when that is a Saturday or Sunday.
- `PRIORITY_DATE` (SF-07-A1): TODAY + 7 calendar days, moved to Monday likewise; after PICKUP plus the 3 working days
  of the way.
- Estimate of the run of 27 November 2026: 3 December for PICKUP 30 November, REQUESTED 11 December.
- Turnaround: 3 working days, the journey way's; Lead's ISO 17294-2:2016 way has 1.

## Connection findings

1. **The feasibility check waits only behind urgent proposed work.** It reads the proposed bookings and keeps those
   of urgent tests in Python, as a test's priority is computed without being stored
   (`sol_laboratory/models/sample_collection/test_request_simulation.py`, `_held_bookings`). Cypress TC-SF07-A1 only declines, so the
   journey is the click-through of an accepted priority.
2. **Receipt does not fix the expected return date on the order path.** The order has an expected return date from
   the moment it is submitted, it is kept when the quotation is sent and copied to the test request at confirmation,
   so the business-flows main path ("otherwise receiving the first sample fixes the expected return date") only holds
   for requests created without an order.
3. **The expected return date is the laboratory's estimate, not the requested date.** The customer asked for
   11 December, the estimate from the pickup day was 3 December, and 3 December stayed the expected return date on
   the order, the portal and the test request, with the requested date shown beside it. The estimate moved once, from
   the first estimate counted from the day of submitting to the one counted from the pickup day Sales typed. The main
   path's "when that estimate meets it, it becomes the expected return date" can be read either way.
4. **The customer can give a requested date and ask for priority only on the cart, before Submit.** The portal order
   page has no control for them after submission, and the order form shows the requested date and the priority badge
   only when they are set (`sale_order_views.xml`), so Sales cannot record a requested date the customer gives later,
   although the SF-07 main path says Sales records it.
5. Sales must give the expected pickup day before deciding on the priority: the field is required and the form marks
   it invalid until it is filled.
6. SF-07-A3 timing, for when it is walked: Change Due Date shows only for statuses waiting, assigned, testing and
   outsourced and only to the head of the testing department (`sample_test_due_date.py:119-123`).
7. Cypress uses RPC throughout this flow: orders at `claimed`, a lab-created request for A3 and the requested date and
   priority request written on the order. No timers, crons or external services are involved in SF-07.
