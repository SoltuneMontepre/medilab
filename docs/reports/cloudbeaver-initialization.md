## Lifecycle and root cause

1. CloudBeaver loads its main configuration and then the runtime file under the workspace. It determines configuration mode from an empty effective server name. `CB_SERVER_NAME` is read later by automatic setup; it does not itself prove completed setup. See [configuration loading](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.server.ce/src/io/cloudbeaver/server/CBServerConfigurationController.java#L79-L109) and [startup](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.server.ce/src/io/cloudbeaver/server/CBApplication.java#L224-L308).
2. H2 schema initialization creates the default teams before administrator creation. The default [initial-data configuration](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/config/core/initial-data.conf) contains `admin` and `user` teams. Users and teams share the authentication subject namespace. User IDs are lowercased before creation, and subject existence is checked across both types. See [security validation](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.service.security/src/io/cloudbeaver/service/security/CBEmbeddedSecurityController.java#L311-L365).
3. Automatic configuration attempts security completion, then saves runtime settings. With requested administrator `admin`, a fresh exact-image reproduction logs the same `User or team 'admin' already exists` call path as the issue. H2 exists afterward, but `.data/.cloudbeaver.runtime.conf` does not. A response from `/status` still says `health: ok`, and GraphQL reports `configurationMode=true`. These are executed local results, not proof of production file contents. See [completion order](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.server.ce/src/io/cloudbeaver/server/CBApplication.java#L535-L573).
4. Without completed runtime settings, another start enters configuration mode and attempts setup again when bootstrap variables remain supplied. Conversely, a completed runtime file prevents automatic setup on normal restarts. An existing **user** is reused by `createAdminUser`; not every existing identifier causes the collision. Rerunning setup can reset that user's supplied password and team memberships, and custom initial-data admin configuration can delete its old initial admin. That is why a name-only change is not a safe recovery strategy. See [database security completion](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.service.security/src/io/cloudbeaver/service/security/db/CBDatabase.java#L254-L343).
5. The [configuration timeout filter](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.model/src/io/cloudbeaver/server/filters/ServerConfigurationTimeLimitFilter.java) explains the reported expired setup period. The [status servlet](https://github.com/dbeaver/cloudbeaver/blob/4cd0be998ea40b03d4e6a29e12bc9f139ba0d080/server/bundles/io.cloudbeaver.server/src/io/cloudbeaver/server/servlets/WebStatusServlet.java) does not gate health on configuration mode.

The immediate collision mechanism is confirmed in 26.2.2. It fits the reported stack trace. Whether production additionally lost a previously valid runtime file, uses an unexpected workspace, has incomplete initialization or has lost data cannot be decided from the logs supplied. The connection overwrite and readiness defects are independently confirmed in the manifests; they do not cause the authentication namespace collision.

## Implementation choices

- Fail closed on ambiguous existing state, interrupted bootstrap and an empty H2 file. An attempt marker alone does not prove whether setup once completed; missing-runtime classification requires the backup-clone audit. The attempt marker contains no credentials and never overrides valid completed runtime settings. Recovery is explicit; there is no automatic deletion, account migration, runtime synthesis or Secret change.
- Compile small Java helpers in the init container using the same pinned image. This avoids adding a registry artifact or installing packages at runtime. Every application start runs the guard; compiled classes alone are ephemeral.
- Provision only a missing connection. Existing connection definitions and saved credentials take precedence, including definitions with obsolete fields that require separately reviewed repair. Secret rotation no longer forces a connection rewrite on restart. The initial seed remains private plaintext unless application credential-storage migration is verified, so workspace backups remain secret-bearing artifacts. Connecting alone did not remove it in the executed 26.2.2 test. An additional authenticated update experiment returned `Session secret controller not found`; encrypted migration is not claimed or forced by this fix.
- Readiness checks disk completion and the application's actual GraphQL configuration state. It does not treat TCP, HTTP 200 from `/status`, a filename, a string `"false"` or a partial/error GraphQL response as proof of readiness.
- The existing Service/IngressRoute and Argo CD self-heal/prune remain in place; the PVC gains its own prune/delete protection. No production repair is automatically added to the GitOps resources.

## Validation

Run `python3 -m unittest discover -s tools/cloudbeaver -v` using a local Docker-compatible engine. All data and credentials in these tests are synthetic. The suite runs the exact image, not a mock of initialization. The Java readiness response tests exercise failure shapes through a local HTTP server.

The regression cases cover collision reproduction, reserved administrator IDs before H2 creation, completed setup, existing administrator plus default admin team, repeated container restarts, replacement containers sharing the same workspace with new ephemeral classes, original-password login despite changed bootstrap inputs, retained users and settings, missing-runtime recovery without H2 mutation, interrupted bootstrap, empty-H2 rejection, malformed JSON preservation, user-managed connections, credential escaping and private file permissions, real PostgreSQL login using saved credentials, and readiness rejection of incomplete setup/errors.

The initial plaintext connection seed is a documented remaining risk protected by private permissions, not a claim of automatic encryption.

## Production recovery boundary

Follow [CloudBeaver recovery](../workflows/cloudbeaver-recovery.md). Before review, obtain the production evidence and choose the recovery branch. After explicit approval, stop the single writer through GitOps, make and restore-test an encrypted cold backup, repair only the verified missing runtime state or complete a demonstrably first-time installation on a clone, then perform the approved GitOps rollout. Never delete/recreate the claim, reset/replace H2, rerun setup against previous users, rotate Secrets or expose the wizard as a shortcut. A Git revert alone cannot undo persistent data changes.
