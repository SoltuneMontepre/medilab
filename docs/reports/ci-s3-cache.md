# Reusing Cypress test results with S3

**Turborepo can reuse a successful test command across commits.** A self-hosted HTTP gateway can store the results on compatible S3 services. An alternative is to keep Task and have GitHub Actions publish and restore verified test reports by content hash. With either option, the cache entry covers one invocation. If login and payments run separately, editing the payments spec can leave login cached. A change to an Odoo component used by both must invalidate both. Wrapping the whole suite in one invocation gives one hit or miss for the whole suite. [Turbo task caching](https://turborepo.dev/docs/crafting-your-repository/caching) · [Turbo remote cache protocol](https://turborepo.dev/docs/core-concepts/remote-caching)

## Options

| Option | What it can reuse | Integration and operating cost |
| --- | --- | --- |
| **Turborepo with an S3-backed HTTP service** | Results of Bun package scripts declared as Turbo tasks | Turbo supports Bun 1.2+ and its remote-cache HTTP API. The third-party Ducktors server supports a custom S3 endpoint. Configure server-enforced read/write permissions such as JWT scopes, since static tokens share one trust domain. This fits a team adopting Turbo for its application packages. It still needs explicit inputs for the Odoo backend. [Turbo caching](https://turborepo.dev/docs/crafting-your-repository/caching) · [Bun support](https://turborepo.dev/docs/support-policy) · [Server storage](https://ducktors.github.io/turborepo-remote-cache/supported-storage-providers.html) · [Server authorization](https://ducktors.github.io/turborepo-remote-cache/environment-variables.html) |
| **Task and GitHub Actions with content-addressed S3 results** | Reports and provenance for each previously successful check with the exact same inputs | Keep the existing commands. The team owns dependency hashing, report validation, producer authorization and orchestration on hits and misses. GitHub's cache service offers an alternative store with documented branch/PR scoping. [Core CI](../../.github/workflows/ci.core.yml) · [GitHub cache scopes](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) |
| **Bazel with bazel-remote and S3** | Bazel test results and build actions shared between runners | Model the checks as Bazel targets and declare their dependencies. The bazel-remote server supports an S3 endpoint and path-style buckets. This requires more migration for MediLab's Taskfile and Odoo services than wrapping existing scripts with Turbo. [Bazel remote caching](https://bazel.build/remote/caching) · [Test cache policy](https://bazel.build/reference/command-line-reference#flag--cache_test_results) · [bazel-remote storage](https://github.com/buchgr/bazel-remote) |
| **Nx with an S3-backed HTTP service** | Successful task results across runners and commits, with the team's bucket holding the artifacts | Define targets around existing commands. Operate a cache service, its credentials and retention. Nx specifies the HTTP API. [Custom commands](https://nx.dev/docs/kb/run-commands-executor) · [Self-hosted cache protocol](https://nx.dev/docs/kb/self-hosted-caching) |
| **Nx Cloud** | The same task results across runners and commits | Managed service with immutable entries. Its read-only CI token can use the shared cache and write to storage isolated to the run. A managed workspace is an option if operating an S3 gateway costs more than using the spare storage saves. [Remote caching](https://nx.dev/docs/features/ci-features/remote-cache) · [CI token scopes](https://nx.dev/docs/kb/access-tokens) |
| **GitHub and Cypress Cloud reruns** | Passed jobs from a previous attempt on the same SHA/ref, or previously passing specs within one recorded CI build | GitHub's failed-jobs rerun preserves successful independent jobs. Cypress Cloud's rerun optimization can select failed specs or tests from a completed run in the same rerun group. Recording and a Business/Enterprise plan or trial are required. Neither operation determines what a new commit changed. [GitHub reruns](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs) · [Cypress Cloud rerun optimization](https://docs.cypress.io/cloud/features/smart-orchestration/rerun-optimization) |

## Turborepo and Task

An isolated local trial with Turborepo 2.11.13 used copies of MediLab's Node settings test and the module it exercises. Both files were declared inputs and the JUnit file `result.xml` was a declared output. The cold run missed. After an unrelated README edit and removal of `result.xml`, the next run hit, skipped Node execution and restored the same SHA-256 for the XML. Editing a declared input produced a miss. [Settings module](../../src/tests/cypress/plugins/settings.js) · [Settings test](../../src/tests/cypress/plugins/settings.test.cjs) · [Turbo inputs and outputs](https://turborepo.dev/docs/reference/configuration)

A second trial disabled Turbo's local cache and ran the same task in three independent directories. Ducktors 3.0.3 used a disposable S3rver 3.7.1 endpoint on the loopback interface. The first runner executed the Node tests and uploaded the artifact. The second changed only README, hit the shared cache and restored byte-identical JUnit XML. The third changed the declared source, missed and executed the tests. The gateway recorded two successful uploads. This verifies the remote task and reporting path with an S3 emulator. The team's provider, deployed authentication and the Odoo browser suite still need a provider-specific trial. [Gateway release](https://github.com/ducktors/turborepo-remote-cache/releases/tag/v3.0.3) · [Upstream S3 emulator tests](https://github.com/ducktors/turborepo-remote-cache/blob/v3.0.3/test/s3.ts)

For remote results, point the Turbo client at the gateway and give only the gateway the provider credentials. Ducktors accepts a custom `S3_ENDPOINT` and bucket. Source files outside the test package can participate in the hash through repository-root globs such as `$TURBO_ROOT$/src/core/modules/**`. Restrict writers at the server or identity provider. A read-only client flag alone does not enforce that restriction. [Storage configuration](https://ducktors.github.io/turborepo-remote-cache/supported-storage-providers.html) · [Authorization](https://ducktors.github.io/turborepo-remote-cache/environment-variables.html) · [Turbo configuration](https://turborepo.dev/docs/reference/configuration)

For a Task-based implementation, calculate an exact key for the group and tested inputs before starting Odoo. On a miss, run the check and publish its reports, artifact digests and successful producer-run identifier only after execution succeeds. On a hit, validate that the producer is trusted and that the group, key and report digests match before reporting success on the current SHA. An incomplete entry or unavailable storage triggers execution. Implement this only if the team wants to maintain these rules itself. [Existing result-reuse proposal](ci-caching.md) · [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

## Nx on the same bucket

The older `@nx/s3-cache` package was offered free with activation and published under a commercial license. Nx deprecated it on 21 May 2026 because of CREEP (CVE-2025-36852). It remains on npm for existing installations and receives no fixes. For a new self-hosted deployment, use the HTTP protocol. [Nx's original licensing announcement](https://nx.dev/blog/custom-runners-and-self-hosted-caching) · [Package metadata](https://registry.npmjs.org/@nx/s3-cache/5.0.7) · [Deprecation notice](https://nx.dev/docs/reference/deprecated/self-hosted-cache-packages)

The MIT-licensed third-party project **thilak-rao/remotecache** implements the Nx protocol. Configure its S3 endpoint, bucket, region and storage credentials on the server. The Nx client uses the gateway's HTTPS URL in `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` and a bearer token in `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`. Maintain the service and its SQLite token store, rotate tokens and configure object expiry on a dedicated cache bucket. [Release v3.3.0](https://github.com/thilak-rao/remotecache/releases/tag/v3.3.0) · [Storage configuration](https://remotecache.dev/guides/storage-strategies/) · [Access tokens](https://remotecache.dev/guides/tokens/) · [Nx configuration](https://nx.dev/docs/kb/self-hosted-caching)

The provider is a third-party S3-compatible service. Its endpoint and credentials were unavailable for testing. Before relying on it, verify a round trip from a runner, permission enforcement, and that object creation honors `If-None-Match: *`. A second write to the same key must return a conflict through the Nx API and preserve the first object. Keep the gateway's storage credentials server-side. Give untrusted jobs read-only access to suitable artifacts, or run them uncached. Keep the full token in a protected CI environment restricted to the trusted producer. [Storage requirements](https://remotecache.dev/guides/storage-strategies/) · [Server security model](https://remotecache.dev/guides/security/) · [GitHub environments](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment)

## A MediLab pilot

1. Start with one independent spec or a fixed group that can run on a fresh demo database. Keep the existing Bun/Task commands and make spec selection explicit. Run the Node tests from the current test script once per workflow or account for them as a separate target. Hash the tested spec, imported support code, fixtures, Cypress config/plugins, lockfile and resolved Node, Bun, Cypress and browser versions. Include relevant flags, runner platform, Odoo modules and demo data, image digests, service configuration and the workflow or scripts that prepare and run the check. Until the backend dependencies of a group are established, invalidate all groups on any relevant backend change. [E2E entry point](../../tools/scripts/test_e2e.sh) · [Test package](../../src/tests/package.json) · [Cypress configuration](../../src/tests/cypress.config.js) · [Task inputs in Turbo](https://turborepo.dev/docs/reference/configuration) and [Nx](https://nx.dev/docs/kb/configure-inputs)
2. Execute every spec while measuring candidate hits on the tested merge tree. Verify that a spec edit invalidates its group, a shared Odoo or helper edit invalidates every affected group, and that skipping a group cannot change the data seen by later groups. The current `push` path skips E2E on `main`. A global cache with read-only PR consumers needs an explicit trusted producer, such as a protected run that actually executes the pilot targets. Without one, new PR results will not warm that cache. [Core CI](../../.github/workflows/ci.core.yml) · [CI timing and result reuse](ci-caching.md)
3. Enable reuse after hits agree with full executions. Keep the required check on the current SHA and run on misses, unavailable storage or uncertain runtime inputs. Store the reports needed by downstream steps as declared outputs, and record the producer and task hash for inspection. Exclude tokens, database contents and user data from artifacts and logs. Compare PR wall time, runner-minutes, hit rate and transfer time with full runs. [Nx task results](https://nx.dev/docs/features/cache-task-results) · [Nx cache security](https://nx.dev/docs/kb/cache-security) · [MediLab pipeline conventions](../conventions/pipeline.md)

## Cypress binary cache

`bunx cypress cache path` locates downloaded binaries and `bunx cypress cache list --size` lists installed versions. On Linux the default directory is `~/.cache/Cypress`. A file-cache adapter such as `tespkg/actions-cache` can restore and save that directory against a custom S3 endpoint. Its GitHub-cache fallback defaults to enabled. Keep `bunx cypress install` after restore. This saves download time while Cypress still executes the selected specs. [Cypress binary cache](https://docs.cypress.io/app/references/advanced-installation#Binary-cache) · [S3 file-cache action](https://github.com/tespkg/actions-cache)
