# Mobile questions

- **Apple developer account.** Decided: the first release is Android only; iOS comes later.
- **Installing the app.** Decided: staff install the Android app from an APK in the `medilab-release` R2 bucket, without Google Play.
- **Printing labels from the phone.** Opening a bottle and preparing a solution print a label (US-T12, US-T13). The phone prints only through its print dialog, AirPrint on iOS or a print service on Android, which not every label printer supports. Do the laboratory's label printers take prints from phones, or is the label printed from a computer afterwards? Default: the label opens as a PDF that the person prints or shares through the phone's system dialog, so a label printer without a phone print service is reached by sharing the PDF to a computer. (blocks US-T31)
- **Working offline.** The app works only online for now: an action without a connection is refused and retried by hand. Laboratories and customer sites can have poor coverage. Should a later version queue actions on the phone and send them when the connection is back, and what happens when the record changed on the web meanwhile? Default: online only; only an unsent photo or signature stays on the phone and is sent again with the same idempotency key, because every other action depends on the record's current state on the server. (blocks US-T30, US-SD04, US-SD05)
- **Automatic updates.** Decided: updates are mandatory, so a phone with an update waiting cannot be used until it has it. Odoo answers whether a phone has an update, and the files are in the `medilab-release` bucket, shared with Medilab Sync's packages.
- **Signing keys.** Decided: the update signing key and the Android upload key are kept in Doppler and read only by the release pipeline; Hoàng Anh keeps their backup.
- **Release bucket.** Is the bucket named `medilab-release`, and what is its public address, from which phones download updates and the APK? Default: `medilab-release`; Odoo needs no address of its own, because the release catalog names each artifact's full HTTPS address. (blocks the release pipeline of Medilab Mobile)
- **First install.** How do staff get the APK the first time: a link or a QR code, and where is it shown, such as on the MediLab sign-in page or sent by an administrator? Default: an administrator sends the address of the latest APK, which the release pipeline prints; MediLab shows no download link, so nothing in Odoo depends on the answer. (blocks the release pipeline of Medilab Mobile)
- **Android versions.** Expo SDK 58 runs on Android 7 (API 24) and later. Does the laboratory have older phones, or should the app require a newer Android version? Default: Android 7 (API 24), Expo's own minimum, so no supported phone is left out. (blocks the release pipeline of Medilab Mobile)
- **Rolling back a code update.** A phone never launches a code update older than the one it runs, so returning phones to the previous version needs that version published again as a new update, signed with the update key that only the release pipeline reads. Should an administrator's rollback in MediLab start the release pipeline, or should the release owner run it? Default: the administrator stops the release in MediLab, which stops new downloads at once, and the release owner runs the pipeline's republish of the previous release, which phones take at their next check; Odoo holds no signing key, as for Medilab Sync. (blocks the Updates of Medilab Mobile)
- **Pushes by default.** Odoo's notification preference chooses between the application and email, and says nothing about pushes. Is a push sent for every event once a person has a signed-in phone, or only for the events the person turns on? Default: on for every event the person is notified of, until they turn it off, because a person who installs the app expects its pushes; a mandatory event's push cannot be turned off. (blocks SH-11)
- **Message text in pushes.** A message in a conversation is written by people and may name a customer, and a push is shown on the lock screen. Should a push of a conversation message show its text? Default: no; the push names the conversation and the author only, so a push to a tester never names a customer, and the text is read in the app. (blocks SH-12)
