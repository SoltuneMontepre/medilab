# Infrastructure questions

- **Bucket names.** What are the names of the main and backup buckets in Object Storage Lite? The architecture calls them `filestore` and `backups`; k3s needs the backup bucket's name to send etcd snapshots there, and `infra/cluster/` uses both names.
- **Laboratory files bucket.** Laboratory files get a private S3-compatible bucket of their own. Is it a third Object Storage Lite plan with the same provider, and does that provider support presigned multipart uploads of files up to 5 GiB, lifecycle rules that abort incomplete multipart uploads, and encryption at rest? Where are its backups kept, outside the provider's site? (blocks US-T23)
- **Sync app address and updates.** Which Odoo address is built into the sync app for production, set as the `MEDILAB_SYNC_ODOO_URL` Actions variable? Is the Tauri update signing key whose public key is in `tauri.conf.json` still available, and should Odoo serve update manifests at `/api/sync/v1/updates`, so that releases can update installed apps?
- **Recovery target.** How long may the system be down when a site is lost, and how many seconds of writes may be lost?
- **Rollback after a migration.** When a release upgrades the modules and then fails, should `cd-core` also restore the database from the pre-release backup, losing writes made since, or leave the newer schema for a person to decide?
- **Maintenance notice.** Are users told before a release window, such as by a banner or an email, and how long before? This applies in `window` mode.
- **MediLab image access.** `ghcr.io/soltunemontepre/medilab` cannot be pulled without credentials. Should the package be made public, like the repository, or should the cluster get a pull token from Doppler?
- **Doppler scope of the cluster.** External Secrets reads the whole `infra` config, which also holds `ANSIBLE_SSH_PRIVATE_KEY` and `K3S_TOKEN`. Should the secrets the cluster reads move to their own config, so that the cluster's token cannot reach the nodes?
- **Filestore storage.** Odoo's filestore is the `filestore` bucket mounted through an S3 CSI driver with GeeseFS. Is a filesystem mount acceptable, or should an Odoo module store attachments in the bucket through its API, with `boto3`, which is already a dependency?
- **Web host name.** Is `lims.soltunemontepre.tech` the production host name of Odoo?
- **Ansible approver.** Who must approve a `cd-ansible` apply? Terraform's `ansible_apply_reviewers` names `hatohui`, the account this was set up from; should it be someone else, or more than one person?
- **SSH from anywhere.** GitHub-hosted runners have no fixed addresses, so port 22 of every node is open to the internet with key-only login for `ansible`. Is that acceptable, or should the runs go through a self-hosted runner or a fixed-address network instead?
- **Password logins on the nodes.** Does anyone log in to Server A with a password? `ssh_hardening_enabled` is turned on once nobody does.

- **ONLYOFFICE activation.** Approve the proposed `office.soltunemontepre.tech` hostname, exact dedicated bucket egress addresses or host-restricting proxy, and storage capacity/encryption/off-node recovery mechanism. Which provider version-history or independent archive proves seven days of actual recoverable bytes despite immediate staging deletion and one-day orphan cleanup? No retention guarantee is established by cache expiry or local-path storage. (blocks EDT-01, EDT-03, EDT-05, OPS-02)
- **ONLYOFFICE operators.** Name the primary and backup infrastructure responders, MediLab maintainer notification destination, private incident destination, and independent dead-man receiver. Confirm a tested path for five-minute notification, thirty-minute acknowledgement/escalation, two-hour triage/progress escalation and a verified outcome or unrecovered classification within twenty-four hours. (blocks OPS-01)
- **ONLYOFFICE timing and licence.** Who accepts the exact pinned-release licence review? If staging cannot keep the aggregate callback work within the current worker/CPU/memory limits while preserving five-minute JWT validation, which total deadline or fetch/worker/caller change is approved with #170? The 21-minute caller timeout alone supplies no aggregate guarantee. (blocks EDT-05, EDT-11, EDT-12)

- **ONLYOFFICE callback compatibility.** If fresh-process tests of the exact committed NODE_CONFIG still reproduce the body-enabled runtime's large-history signature/payload disagreement, which remediation may be evaluated: an upstream final-payload-signing correction with a reviewed rebuild, a tested release, or a proven supported delivery mode? The purported JWT_IN_BODY=false reproduction was withdrawn because effective process configuration was not established. No image/digest change or authentication relaxation is authorized by that finding; source/licence and real callback acceptance remain required. (blocks EDT-02, EDT-05, EDT-11, EDT-12)

- **Operator file access.** Recovery accepts explicit CA/secret/output paths, including protected absolute paths outside the checkout; offline schema validation reads operator-selected CRDs and manifests. Should these tools continue to run under the operator's filesystem permissions, or enforce a configured list of trusted read/write roots? Specify the allowed roots before restricting the documented recovery contract. SonarCloud reports pythonsecurity:S8707 on these CLI paths; security-owner review remains required and no finding is accepted or suppressed.
